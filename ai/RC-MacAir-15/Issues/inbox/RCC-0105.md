Document and correct the terminology confusion that surfaced while planning assistant reply chrome, chat turn metadata, bookmark/note storage, and chat-id copy behavior.

This confusion matters because it could lead a worker to implement new chat UI metadata in the wrong layer: the retired Kimi wire path, raw harness interpreters, frontend compatibility aliases, or unsaved live-stream state instead of the canonical chat event and SQLite exchange path.

## What Happened

During planning, the new WebSocket/application messages for chat-turn metadata were described as "wire" messages. That wording was ambiguous inside this codebase.

The intended meaning was:

- Add app-level WebSocket messages such as `chat-turn:metadata:update`, `chat-turn:metadata:updated`, and `chat-turn:metadata:error`.
- Store bookmark/note metadata on saved SQLite chat exchanges.
- Gate assistant reply chrome on the completed and saved exchange id.
- Keep raw harness protocols and old Kimi compatibility paths out of the feature.

But the word "wire" can also point to older or lower-level systems in this repository, including historical Kimi `--wire` work, backend `lib/wire/*` files, raw harness event translation, WebSocket fanout, and frontend stream handlers.

## Why It Occurred

The codebase has overlapping meanings for "wire":

- Historical Kimi `--wire` protocol language still appears in older docs, tickets, scripts, or compatibility code.
- Active backend files under `fusion-studio-server/lib/wire/` still use the term for canonical event bridging and WebSocket fanout.
- Harness adapters translate provider-specific output into canonical chat events before the app event bus sees them.
- Frontend code receives WebSocket messages and turns them into `StreamSegment[]`, but that is not the raw provider protocol.
- The planning discussion used "wire" casually for application-level messages, which made it unclear whether the feature belonged near harness protocol parsing, canonical server events, or frontend chat state.

## Culprits

- Overloaded naming: `wire` means too many things in the current repository.
- Legacy Kimi terminology remains searchable enough that a worker can accidentally use it as current architecture.
- The active Chat System relies on a multi-stage flow that is easy to conflate:
  - OpenCode/provider output
  - backend harness translator
  - canonical harness events
  - backend universal event bus
  - SQLite persistence
  - WebSocket broadcast
  - frontend stream interpreter
  - React message rendering
- Existing `turn_end` broadcast timing can be mistaken for durable save completion, even though reply chrome needs the saved `exchanges.id`.
- Current exchange persistence does not clearly return or broadcast the inserted exchange id to the frontend as part of the finalization path.

## Risks If Not Fixed

- A worker could add bookmark/note metadata handling to old Kimi protocol code or raw harness parsing.
- New UI metadata could bypass SQLite exchange metadata and be lost on reload.
- Reply chrome could render before the assistant exchange is saved, leaving Copy/Bookmark/Chat ID actions without a valid chat id.
- Chat ID copy could accidentally copy `threadId` instead of `exchanges.id`.
- Notes could leak into broad debug/live logs if new metadata messages are not added to redaction rules.
- Duplicate frontend handlers could be added around compatibility aliases instead of the active WebSocket/chat-state path.
- Stop/interrupted turns could behave differently from normal completed turns if both paths are not gated on the same saved-exchange ack.

## Correct Architecture For This Feature

Use these terms in the spec and implementation:

- **Harness protocol**: provider-specific output from OpenCode or any future adapter. Do not add bookmark/note/chrome behavior here.
- **Backend canonical chat events**: normalized server-side events emitted onto the universal event bus.
- **SQLite exchange**: durable chat pair row in `exchanges`; its `id` is the chat id.
- **WebSocket application message**: app-level client/server messages for metadata updates and saved-exchange acknowledgements.
- **Frontend stream interpreter**: client code that turns WebSocket chat events into message state and `StreamSegment[]`.
- **Reply chrome**: React UI rendered only after the assistant reply is complete and the saved `exchangeId` is available.

Expected completion flow:

1. Assistant tokens stream, or Stop is clicked.
2. The current turn finalizes through the server-owned path.
3. The assistant exchange is saved to SQLite.
4. The inserted `exchanges.id` is made available to the frontend.
5. Reply chrome renders.
6. The composer leaves the unclickable spinning finalization state and returns to Send.

## Corrective Work

- Update the assistant reply chrome spec to avoid ambiguous "wire" wording for app-level messages.
- Add a short Chat System wiki section that names the active harness/event flow and explicitly marks old Kimi wire paths as historical/compatibility-only.
- Audit chat-related tickets/specs for casual "wire" usage and replace it with a specific layer name.
- Add implementation guidance that new bookmark/note/chrome code must not import or modify retired Kimi protocol paths.
- Ensure new metadata WebSocket messages and note bodies are covered by redaction rules before any note persistence work lands.
- Ensure the chat turn completion path exposes saved `exchangeId` for both normal completion and interrupted/Stop completion.

## Acceptance Criteria

- Future workers can tell exactly where bookmark/note/chat-id behavior belongs.
- The spec uses "WebSocket application message" or "backend canonical chat event" instead of generic "wire" where appropriate.
- The Chat System wiki documents the active flow from harness translator through universal event bus to frontend stream rendering.
- Old Kimi wire paths are labeled historical or compatibility-only in relevant docs.
- Assistant reply chrome is gated on saved SQLite `exchangeId`, not just streamed `turn_end`.
- Chat ID copy uses `exchanges.id`, never `threadId`.
- Note and metadata update messages are redacted from logs where needed.
