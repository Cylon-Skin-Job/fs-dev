## Goal

Extract reusable React presentation and dismissal primitives for Fusion Studio's modal and overlay surfaces while preserving every existing state owner, command handler, WebSocket path, filesystem operation, and feature-specific lifecycle.

This work should be safe to run beside the Provenance roadmap because it does not invent provenance schemas, move business-action ownership, or create a second mutation/event path.

## Findings

Fusion Studio currently has several distinct overlay families:

- App-level dialogs and modals, including workspace add/create, theme picker, secrets manager, browser bookmarks, calendar events, and assistant-reply bookmarks.
- A trigger-driven modal system under `components/Modal/` with an imperative bridge in `lib/modal.ts` and feature actions such as `fireModalAction()`.
- Hover-positioned surfaces already sharing `hover-icon-modal` primitives and state behavior.
- Drawers, menus, and popovers with positioning and focus semantics different from dialogs.
- Transient visual/status layers such as connecting and screenshot-flash overlays.
- Full application surfaces such as `FusionOverlay`, which are not merely modal dialogs.

These surfaces repeat visual shell concepts, but they do not share one behavioral contract. Reuse should be organized by interaction family instead of forcing every file named Modal or Overlay through one global controller.

The current `ModalOverlay` is not a universal application modal host. It specifically mounts server/trigger-defined modal configurations, selects a subtype renderer, injects bounded styles, and forwards feature actions through `lib/modal.ts`. It should consume shared presentation primitives eventually, but it must not become the state or command owner for unrelated feature dialogs.

## Reusable Layer Boundary

The reusable layer may own:

- Backdrop and frame markup.
- Header/title layout and close button.
- Body and footer slots.
- `role="dialog"`, `aria-modal`, labelling hooks, and other dialog accessibility structure.
- Escape and backdrop-dismiss behavior.
- A typed close reason such as `escape`, `backdrop`, `close_button`, `cancel`, or `completed`.
- Stable class-name extension points needed to preserve current styling during migration.

The reusable layer must not own:

- Feature open/closed state or form state.
- Zustand stores or workspace/session identity.
- WebSocket messages, Electron IPC, filesystem operations, or server commands.
- Confirm/cancel business behavior.
- Trigger dispatch or `fireModalAction()`.
- UI action IDs, provenance seeds, event publication, ledger storage, or provenance admission.
- A global modal queue or command router.

## Proposed Parts

Create a small package such as:

```text
fusion-studio-client/src/components/overlays/
├── OverlayBackdrop.tsx
├── DialogShell.tsx
├── DialogHeader.tsx
├── DialogFooter.tsx
├── DialogCloseButton.tsx
├── useDialogDismiss.ts
└── index.ts
```

Names may change after a focused inventory, but each part should remain presentation-only. Prefer composition and slots over a configuration object that attempts to encode every feature.

Do not introduce a React portal in the first slice. Moving existing surfaces to `document.body` can change stacking contexts, focus, positioning, scroll containment, and click propagation. Portal ownership should be a separately tested decision after the primitive extraction is stable.

## Safe Initial Consumers

Migrate one consumer at a time, preserving its current state owner, handler identity, DOM placement, CSS classes, and user-visible behavior. Good initial candidates are:

1. `components/secrets/SecretsManagerModal.tsx`
2. `components/chat/AssistantReplyBookmarkModal.tsx`
3. `components/browser/BookmarkDialog.tsx`
4. `components/calendar/EventModal.tsx`

The existing hover-icon modal family should remain separate and reusable in its current interaction domain. It may share low-level tokens later, but it should not be folded into dialog state/dismissal behavior.

## Deferred Or Excluded During Provenance Work

Do not behaviorally migrate these surfaces while their owning systems are active Provenance or concurrent-work targets:

- `WorkspaceAddModal` and `WorkspaceCreateModal`: workspace transition and command ownership overlaps SPEC-32b0.
- `ModalOverlay`, `AlertModal`, and `DragFileModal`: trigger/modal side effects and workspace-generation currency overlap SPEC-32e.
- Theme picker: theme lifecycle participates in SPEC-32.
- Wiki/File command surfaces: first SPEC-34 adapter pair.
- Office menus, popovers, and overlays: active concurrent Office work and later provenance adapters.
- `FusionOverlay`: full application surface with its own composition and navigation behavior.
- Connecting and screenshot-flash overlays: transient status/effect layers rather than dialogs.
- Drawers, context menus, and positioned popovers: separate interaction families that require their own inventory and primitives.

After the owning work settles, a deferred surface may adopt the presentation primitives without moving its command path.

## Provenance Compatibility

Do not create provisional provenance fields or schemas in this refactor. In particular, do not add `uiActionId`, `uiActionSeed`, ledger/event publication, workspace authority lookup, or new wire fields to shared overlay components.

The future provenance attachment point is the feature-owned business handler, not the dialog shell. The operational command remains authoritative and executes exactly once. A later approved provenance adapter may observe that command through the SPEC-34/40 fail-open path without turning the reusable component into an authorization or identity owner.

Renderer-only SPEC-34 preparation and later wire enablement remain owned by the Provenance roadmap. This ticket must not pre-implement or reinterpret those contracts.

Old rendering implementations may remain temporarily while consumers migrate, but old and new business-action paths must never both execute. Each migrated feature keeps exactly one authoritative confirm, cancel, and close handler.

## Suggested Slices

### Slice A - Inventory And Behavioral Contract Tests

- Inventory dialog/modal DOM, dismissal rules, focus expectations, CSS classes, state owners, and action handlers.
- Classify each surface as dialog, popover/menu, drawer, transient layer, or full application surface.
- Add focused tests for Escape, backdrop click, inner click propagation, close button, confirm, cancel, and feature state preservation for the selected initial consumers.
- Record deferred surfaces and their owning roadmap/ticket.

### Slice B - Pure Primitives

- Add presentation-only dialog/backdrop/header/footer/dismissal parts.
- Add no store, WebSocket, Electron, filesystem, trigger, or provenance imports.
- Preserve consumer DOM placement and class extension points.
- Add primitive accessibility and dismissal tests.

### Slice C - First Consumer Pair

- Migrate Secrets Manager and assistant-reply bookmark dialogs.
- Preserve their existing state and action owners.
- Verify no command, metadata, or clipboard behavior changed.

### Slice D - Second Consumer Pair

- Migrate browser bookmark and calendar event dialogs.
- Preserve their current state and action owners.
- Re-run the full focused dialog suite and client build.

### Slice E - Deferred-Surface Reassessment

- Recheck Provenance and Office completion state.
- Decide individually whether the trigger-driven modal system, workspace dialogs, and theme picker can consume the primitives without overlapping active owners.
- Do not treat reassessment as automatic permission to migrate every overlay family.

## Acceptance Criteria

- Shared dialog/backdrop/header/footer/dismissal primitives exist and are presentation-only.
- Initial migrated consumers preserve their current open state, form state, confirm/cancel behavior, CSS, DOM placement, and visible layout.
- Escape, backdrop click, inner click, close button, confirm, and cancel behavior have focused tests.
- Dialog accessibility structure is consistent and labelled.
- No new global modal store, modal queue, command dispatcher, WebSocket message, or Electron IPC path is introduced.
- No shared primitive imports feature stores, networking, filesystem, trigger, or provenance modules.
- No `uiActionId`, `uiActionSeed`, canonical event, ledger, or workspace-authority behavior is introduced by this ticket.
- Each user action still reaches exactly one pre-existing authoritative business handler.
- Workspace, trigger-driven, theme, Wiki/File, Office, full-surface, drawer, popover, and transient overlay exclusions are respected until their owning work permits migration.
- Existing hover-icon modal behavior remains intact.
- `npm run build` passes in `fusion-studio-client`.
- Focused component tests and applicable browser smoke tests pass.

## Non-Goals

- Redesigning modal visuals.
- Replacing all overlays with one component.
- Introducing a portal or focus-trap dependency in the first slice.
- Centralizing feature state.
- Changing command, mutation, or trigger semantics.
- Implementing Provenance roadmap slices.
- Migrating every modal or overlay in one change.
