## Decision Update — 2026-07-14

The original `WorkspaceSwitcher` drawer work is complete and obsolete. The current ribbon interaction is the intended design:

- Click the workspace title in the header to open or close the ribbon.
- Hold Option and press Left/Right to preview workspaces.
- Continue pressing Left/Right to move through the ribbon.
- Release Option to commit the highlighted workspace.
- Use the ribbon `+` menu to restore a registered workspace that is hidden from the ribbon.
- Use the ribbon `×` button to hide a workspace from the ribbon without unregistering it.

Do not add `Cmd+Shift+W` or another ribbon-toggle shortcut. Option+Left/Right and the clickable header are the canonical keyboard and pointer paths.

The Electron `Workspaces` menu is now redundant and should be removed. The rest of the native application menu remains in place.

The remaining substantive work is to make ribbon removal a complete renderer-memory boundary. Hiding a workspace should release its display/render state from client RAM while leaving durable workspace state and server-owned background activity intact.

---

## Outcome

After this ticket:

1. Workspace switching and ribbon membership are managed only through the in-app ribbon.
2. Removing a workspace from the ribbon evicts that workspace's renderer display caches.
3. Reopening the workspace rebuilds the display from its workspace/view JSON state and normal discovery APIs.
4. Server-owned threads, triggers, watchers, agents, and other background work continue while the workspace is hidden.

Hiding from the ribbon is not unregistering, deleting, stopping, resetting, or suspending a workspace. It only removes the workspace from the visible working set and releases renderer memory used to display it.

## 1. Remove The Electron `Workspaces` Menu

Remove the top-level native `Workspaces` menu and its renderer/main-process bridge.

Delete:

- `workspaceMenuState`, `sanitizeWorkspaceMenuState()`, `setWorkspaceMenuState()`, and `buildWorkspacesSubmenu()` from `fusion-studio-client/electron/main.cjs`.
- The top-level `{ label: 'Workspaces', ... }` menu entry.
- The `workspace-menu:set-state` IPC listener in the Electron main process.
- `setWorkspaceMenuState()` from the preload bridge.
- `WorkspaceMenuState` and `WorkspaceMenuItem` renderer types.
- Workspace-specific `ElectronMenuAction` variants.
- Workspace registry synchronization and workspace-menu action cases from `useElectronMenu.ts`.

Keep:

- The native application, File, Edit, View, and Tools menus.
- `onMenuAction` and the non-workspace native menu actions used by themes, secrets, and connectors.
- The renderer ribbon, header title button, Option+Left/Right behavior, Add Project, Create New, add-to-ribbon, remove-from-ribbon, and ribbon reorder behavior.

Do not replace the removed menu with another native workspace menu or keyboard shortcut.

## 2. State Ownership

Use three explicit state classes.

### Durable Workspace/View State

Durable UI state belongs in the workspace folders:

```text
ai/<machine>/System/state/state.json
ai/<machine>/Views/<NNN-view-id>/state/state.json
```

Examples include the active view, pane geometry, view mode, open tabs, selected document/page, navigation history, and scroll positions when those values are intended to survive reopening.

This JSON is the source of truth after a workspace has been removed from the ribbon. Do not maintain a second durable `workspace-cache.json` representation. The old server runtime-cache module has already been removed and must not be reintroduced.

Any display state that should survive close/reopen must be written to the appropriate workspace or per-view JSON file during normal state mutations. State that is intentionally transient may return to its default when the workspace is rebuilt.

### Renderer Display Cache

Renderer display cache exists only to make currently visible ribbon workspaces fast to revisit. It includes, but is not limited to:

- `panelStore.workspaceState[workspaceId]` and the live panel/view render state it mirrors.
- File-tree nodes, expanded-folder maps, loaded file contents, rendered tabs, and other file-viewer objects for that workspace.
- Wiki tree/content objects and rendered navigation state.
- Issue/ticket board data and selected/expanded ticket UI.
- Agent-view data, expanded agent/workflow UI, and loaded prompt/config content.
- Office/document/capture render models and scroll/selection objects.
- Workspace screenshot data URLs and active-panel preview metadata.
- Pending renderer requests, timers, prefetches, and subscriptions that can repopulate a hidden workspace's display cache.

This state may remain in RAM during an ordinary switch between workspaces that are still in the ribbon. It must not remain in RAM after the workspace is removed from the ribbon.

### Server Runtime And Background Work

Server-owned runtime is not renderer display cache. Ribbon removal must not stop or discard:

- Active or queued thread/harness work.
- Live turns and server-owned thread runtime state.
- Trigger registrations, cron timers, holds, or trigger-created work.
- Filesystem watchers or background services.
- Agent/background-worker runs.
- Durable database rows, messages, tickets, events, or project files.

Do not send stop, interrupt, cancel, unregister, watcher-close, harness-shutdown, or process-kill actions from the ribbon-removal path.

Background work must be able to finish while its workspace is hidden. Its results are discovered from the server/durable files when the workspace is reopened.

## 3. Ribbon Removal Lifecycle

Keep the existing request/event names unless a concrete protocol change is required:

```text
workspace:ribbon_remove_requested
workspace:registry_changed
workspace:switched
workspace:ribbon_removed
```

When the `×` button removes a workspace from the ribbon:

1. Set only the registry row's `ribbon_visible` membership field to false.
2. If it was active, switch to the nearest remaining ribbon workspace, or the zero-ribbon empty state.
3. Complete any already-accepted durable state write without creating a new renderer cache snapshot.
4. Evict every renderer display/cache entry belonging to the hidden workspace.
5. Cancel or invalidate renderer-side requests that could write the hidden workspace back into memory after eviction.
6. Leave server runtime and durable files running/unchanged.

For active removal, the new workspace must become active before live unkeyed UI stores are reset or hydrated. Do not clear data that already belongs to the newly active workspace.

For inactive removal, evict only the named workspace. Do not disturb the active workspace's live display state.

### Late-Response Safety

Async responses must carry enough workspace identity or generation information to be rejected after a switch/removal. A late `state:result`, screenshot response, file response, tree response, wiki response, or panel-discovery response from the hidden workspace must not repopulate the current workspace or recreate the evicted cache.

---

## 4. Reopen/Hydration Lifecycle

When a hidden registered workspace is selected from the ribbon `+` menu:

1. Set `ribbon_visible` to true and append it to ribbon order.
2. Switch to it when requested by the existing ribbon flow.
3. Start from an empty renderer display cache for that workspace.
4. Read workspace shell state from `System/state/state.json`.
5. Discover the workspace's current view registry and view folders.
6. Load each needed view's state from `Views/<NNN-view-id>/state/state.json` through the existing `state:get` path.
7. Rebuild file tabs, selected pages/documents, navigation, geometry, and other durable UI state from those files.
8. Fetch current server/domain data normally, including work completed while the workspace was hidden.

Do not resurrect a previously retained Zustand object graph. A useful proof is to change a view's JSON state while the workspace is hidden and confirm that reopening uses the changed file value rather than the pre-close render value.

---

## 5. Known Gaps To Audit

The current implementation handles only part of the renderer boundary:

- `workspace:ribbon_removed` calls `panelStore.evictWorkspaceRuntimeState()` and `fileStore.evictWorkspaceTree()`.
- `fileStore.tabs` and `activeTabPath` are global and survive workspace activation/removal even though file tabs are now persisted in the file-viewer's `activity.tabs` state.
- `hydrateTabsFromActivity()` exists but is not currently wired into `state:result` hydration.
- `ticketStore` keeps global ticket data and `activeTicket` without workspace identity or a targeted eviction/reset path.
- `agentStore` keeps global agent data, expanded agent/workflow selection, and loaded file content without workspace identity or a targeted eviction/reset path.
- `screenshotStore` retains per-workspace PNG data URLs and active-panel metadata after ribbon removal.
- `fileDataStore` keys are not workspace-scoped and currently depend on broad clearing during workspace switch.
- Per-view `state:result` messages are keyed by view id but not workspace id, so late responses can cross a workspace boundary.

Audit the remaining view/component stores for the same pattern. Do not solve this by retaining a hidden workspace's render graph under a different cache key.

## 6. Acceptance Criteria

### Native Menu

- No top-level Electron `Workspaces` menu is present.
- No workspace-menu snapshot IPC or workspace-specific native menu action remains.
- Native Tools/theme/secrets/connector actions still work.

### Ribbon UX

- Header click opens/closes the ribbon.
- Option+Left/Right previews and cycles; releasing Option commits the highlighted workspace.
- Repeated Left/Right presses continue cycling before Option is released.
- Ribbon `+` lists hidden registered workspaces and can restore them.
- Ribbon `×` hides without unregistering.
- Removing the final visible workspace shows the existing zero-ribbon state.
- No new ribbon-toggle shortcut is added.

### Renderer Memory

- Removing an inactive workspace evicts only that workspace's renderer caches.
- Removing the active workspace switches first, then removes all old-workspace render/cache objects without clearing the new active workspace.
- Hidden-workspace panel/view state, file trees/content/tabs, wiki content, ticket/agent UI, screenshots, and pending renderer work are absent from client memory.
- Late responses cannot recreate hidden-workspace state or contaminate the active workspace.
- Ordinary switching between still-visible ribbon workspaces may retain the existing fast-return cache.

### Rehydration

- Reopening starts with no retained renderer snapshot for that workspace.
- Workspace shell and view state are loaded from the workspace/view JSON files.
- File tabs hydrate from the file-viewer's persisted `activity.tabs` state rather than a global pre-close array.
- Wiki/document scroll and selection are taken from the view's JSON state when defined.
- Current server/domain data is fetched again, including changes produced while hidden.

### Background Continuity

- A live server-owned thread or agent run continues after its workspace is hidden.
- A trigger/cron/background job can fire and finish while the workspace is hidden.
- Reopening exposes the completed work through normal server/disk hydration.
- Ribbon removal does not stop, interrupt, unregister, or delete server-owned work.

### Durability And Safety

- Workspace registration remains intact except for `ribbon_visible` and ribbon ordering changes.
- Project content, database rows, view registry files, and state JSON files are not deleted or reset on ribbon removal.
- No 24-hour grace period, close timestamp, cleanup timer, or server `workspace-cache.json` is introduced.
