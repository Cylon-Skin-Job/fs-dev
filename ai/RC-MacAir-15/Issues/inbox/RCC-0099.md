## Fingerprint Prototype Notes

A provisional Node script was added at `fusion-studio-server/scripts/machine-fingerprint.js` to explore what first-run machine capture can collect on this Mac.

The script currently:

- Accepts `--name RC-MacAir-15` and emits a filesystem-safe `slug`.
- Reads macOS hardware data through `system_profiler SPHardwareDataType`.
- Reads platform identifiers through `ioreg -rd1 -c IOPlatformExpertDevice`.
- Attempts `sysctl` for memory, CPU model, model identifier, and CPU count; if `sysctl hw.memsize` is denied, it derives RAM from `system_profiler`.
- Produces a `stableFingerprint` hash from stable-ish identifiers such as platform, architecture, model identifier, hardware UUID/platform UUID, provisioning UDID, serial number, and board id when available.
- Produces a broader `diagnosticFingerprint` hash that also includes CPU/RAM/OS diagnostic hints.
- Redacts sensitive raw identifiers by default while still using the raw values locally for hashing.
- Supports `--show-sensitive` for explicit local debugging of raw serial/UUID fields.

The manual SQLite seed used a simple `system_config` shape:

- `local_machine_name`: string value containing the active machine slug.
- `local_machine_identity`: JSON payload containing `schemaVersion`, `seededManually`, `machineId`, `givenName`, `slug`, `hostname`, `platform`, `arch`, `stableFingerprint`, `diagnosticFingerprint`, `hardwareHints`, and notes.

This shape is only a prototype. Future startup/onboarding work should decide whether the accepted canonical schema remains `system_config`, moves to a dedicated `machines` table, or uses both a canonical table and a cached config key. The important product decision remains: the app-owned `machine_id` is the durable identity, while fingerprints are matching/diagnostic hints and the given name/slug are editable labels.

## Startup / First Run

On app startup:

- Detect whether a current machine identity exists in internal SQLite.
- Detect whether the active repo contains a matching `ai/<machine-name>/machine.json`.
- If both exist and match, continue startup normally.
- If SQLite exists but `machine.json` is missing, recreate the manifest from SQLite.
- If `machine.json` exists but SQLite is missing, register the machine in SQLite from the manifest.
- If neither exists, enter first-run machine setup.
- Before showing the first-run wizard panel, capture the local machine fingerprint/hardware hints.

## Machine Information Capture

Collect non-sensitive local machine information for defaults and diagnostics:

- OS hostname.
- Platform.
- CPU model or architecture where available.
- RAM amount where available.
- Other stable-ish local identifiers available through Electron/Node APIs, if safe and non-sensitive.
- App-generated stable `machine_id`.
- Proposed/default machine name.
- Machine slug used for `ai/<machine-name>/`.
- Creation and last-seen timestamps.

Do not use the OS hostname or hardware details as the stable primary key. Hostnames may be generic or change later, and hardware can be upgraded. Use collected machine facts as matching hints for first-run recovery and diagnostics. The permanent identity is the app-generated stable `machine_id`.

## First-Run Wizard

Create a first-run wizard with a machine naming panel.

Requirements:

- Capture machine fingerprint/hardware hints before showing the machine naming panel.
- Show a suggested name derived from local machine info when possible.
- Let the user edit the name before confirmation.
- Validate the name as a filesystem-safe slug or generate a filesystem-safe slug from the display name.
- Explain that the machine name is used for the repo-local AI namespace.
- On confirmation, bind the generated stable machine id, captured fingerprint/hardware hints, and user-given machine name in SQLite.
- On confirmation, create/update `ai/<machine-name>/machine.json`.

## Folder Creation

After the user confirms the machine name:

- Create `ai/<machine-name>/` if it does not exist.
- Create or validate expected machine-scoped folders such as `Views`, `Wiki`, `Issues`, `Office`, `Captures`, `Data`, `System`, `Agents`, `Prompts`, `Scripts`, `Skills`, and `Tools` according to the active ai-v2 structure.
- Do not overwrite existing collaborator machine folders.
- Create the machine folder and subfolders inside the default workspaces that ship with the app.
- When a new workspace is added later and the AI folder is created, also create the current machine's folder and expected subfolders alongside it.

## Migration / Rename Handling

Machine rename is not an inline normal workflow.

If a user needs to rename a machine later:

- Generate a dedicated rename/migration ticket.
- Run scripts to rename the repo folder and/or update SQLite rows.
- Preserve the stable `machine_id`.
- Update `machine.json`.

## Acceptance Criteria

- First run prompts the user to name the machine.
- First run captures machine fingerprint/hardware hints before the naming panel.
- Startup can recover when SQLite exists but `machine.json` is missing.
- Startup can recover when `machine.json` exists but SQLite registration is missing.
- Existing matching SQLite and `machine.json` state starts without prompting.
- Machine identity includes stable `machine_id` plus user-given machine name/slug.
- Startup never treats OS hostname alone as a stable machine identity.
- The flow creates/validates `ai/<machine-name>/` without overwriting other machine namespaces.
- Default shipped workspaces receive the current machine folder/subfolders.
- Newly added workspaces receive the current machine folder/subfolders when their AI folder is created.
