Build the protected-change approval system for System Manager.

Normal workspace agents should be able to read system guidance and request system-level changes, but they must not directly edit protected files such as prompts, `TRIGGERS.md`, tool definitions, skill definitions, connector configuration, or cross-workspace automation rules.

## Goal

Create a governed request/approval path where local agents can propose protected changes and System Manager decides whether to block, request user approval, or institute the change.

## Protected Files / Behaviors

Protected areas include:

- Prompt files that define tool scope or workflow behavior.
- `TRIGGERS.md` or trigger-like files that can execute scripts or wake workflows.
- Tool and skill definitions.
- Connector configuration.
- System templates and cross-workspace automation rules.
- Any workflow that can access secrets, call external services, write files outside the local workspace root, or launch scripts.

## Risk Model

A local agent editing protected files directly could create unsafe behavior, such as:

- Writing a trigger that fetches secrets and passes them into a prompt.
- Sending sensitive data outside the system without user awareness.
- Creating scripts that bypass normal tool safeguards.
- Granting itself or another workflow broader tool access.
- Turning a harmless automation request into recurring unsafe behavior.

## Proposed Flow

Local agent flow:

1. User asks for a system-level behavior or automation.
2. Local agent reads relevant wiki/prompt guidance.
3. Local agent cannot directly edit protected files.
4. Local agent calls a future request tool, such as `request_trigger` or `request_protected_change`.
5. The request is filed to System Manager with structured context.

System Manager flow:

1. Receive protected-change request.
2. Inspect source workspace, thread history, user wording, proposed files, and proposed diff/body.
3. Apply System Manager criteria.
4. Return one of:
   - `blocked`
   - `approval_needed`
   - `instituted`

## Request Payload

Future request tool should include:

- Source workspace id/path.
- Source thread id.
- Relevant chat history or excerpts.
- Requested operation: create, update, delete, or replace strings.
- Target file path.
- Proposed file body or diff.
- Summary of intended behavior.
- Claimed user approval context.
- Risk classification if known.

## Approval UX

When approval is needed, System Manager should prepare the change and present:

- Concise summary of what will change.
- Why the change is being requested.
- What capabilities the trigger/prompt/tool would gain.
- Inline `Approve` action.
- Click-to-view file or diff preview.
- Option to reject or ask for revision.

## Trigger Design Direction

Triggers should be pared down to essentials:

- Wake at a bounded moment or event.
- Evaluate simple criteria.
- Fetch bounded context if needed.
- Pass scoped data to a deterministic custom tool.
- Avoid open-ended scripting or broad filesystem/network behavior.

## Example Future Workflow

User asks for a music-discovery automation that finds recent YouTube links in a genre, checks what is buzzworthy, compares against listening history, and returns a curated list.

Safe shape:

- Narrow trigger wakes the workflow.
- Deterministic search tool fetches bounded YouTube/catalog results.
- Deterministic verification confirms candidate existence and metadata.
- Assistant ranks candidates using a prompt and local preference ledger.
- Preference ledger evolves from user feedback: more of this, less of that, explanation notes.
- Any new trigger behavior is proposed through System Manager approval before it can run.

## Out Of Scope

- Implementing the full tool system.
- Implementing `request_trigger` immediately.
- Building the approval UI immediately.
- Building the music-discovery automation itself.

## Acceptance Criteria

- Protected-change approval flow is specified.
- Request payload shape is defined.
- System Manager outcomes are defined.
- Trigger safety constraints are documented.
- The ticket can guide later implementation without blocking current prompt/frontmatter work.
