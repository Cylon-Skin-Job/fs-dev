## Goal

Remove two unwanted Fusion Studio subsystems completely:

1. OpenCode thread forking and its pending-fork architecture.
2. Fusion-managed clipboard history, including its composer control, automatic
   monitor, private storage, protocol, events, and dormant UI implementations.

The fork and clipboard-history controls have already been removed from the
visible composer. Their underlying subsystems remain until this ticket is
implemented.

Clipboard-history removal does **not** mean disabling normal macOS copy and paste.
Direct user-initiated copying through `navigator.clipboard` or an equivalent
small platform utility must continue to work without recording a Fusion history.

## Why

The fork feature creates a new persisted Fusion thread at click time, copies
saved exchanges, stores `pendingFork` metadata, and delays the actual OpenCode
`--fork` operation until the first prompt. The clipboard-history feature adds a
second broad stack: renderer state and popovers, optional system-clipboard
polling, WebSocket messages, UEB events, secret detection, SQLite metadata,
macOS Keychain values, deduplication, pruning, redaction rules, and broadcasts.

Neither subsystem is part of the desired product surface. Leaving their dormant
or partially hidden implementations in place makes future chat, persistence,
security, and runtime work preserve unnecessary behavior.

## Fork Implementation To Remove

- Composer fork action hook and its thread-metadata refresh behavior.
- Client `thread:forked` handling and fork-specific TypeScript types.
- Server `thread:fork` WebSocket handler.
- `thread-fork-service.js`, including copied-exchange and chat-mirror creation.
- OpenCode `pendingFork`, `forkProvenance`, and `--fork` startup behavior.
- Dedicated fork service, WebSocket, harness, and restart compatibility tests.
- Active CSS and current documentation that present fork as a supported action.

Archived specifications may remain as clearly historical records; they must not
be presented as current product behavior or implementation guidance.

## Clipboard-History Implementation To Remove

- Composer `ClipboardTrigger` and all clipboard-history popover styling.
- The active shared-hover-modal trigger plus the older exported
  `ClipboardPopover` and interaction-controller paths.
- Clipboard Zustand state, client request API, types, subscriptions, and startup
  initialization.
- The opt-in one-second `navigator.clipboard.readText()` monitor and its
  local-storage configuration.
- Client and server `clipboard:*` WebSocket messages and routing.
- Clipboard broadcasts and `clipboard:added`, `clipboard:used`,
  `clipboard:deleted`, and `clipboard:cleared` UEB publication.
- Server clipboard backend, index access, Keychain access, secret detector,
  deduplication, rolling-cap behavior, and value-specific log redaction rules.
- `clipboard_index` active schema and all focused clipboard-history tests.
- `writeAndRecord` use by assistant reply, Chat ID, and note copy actions. Those
  actions must remain capable of a normal one-time system clipboard write but
  must not retain a Fusion history copy.
- Current documentation describing Fusion clipboard history or its monitor as a
  supported capability.

Historical migration files must remain intact so existing Knex migration chains
stay valid. Add a new forward migration for active-schema removal instead of
rewriting or deleting migrations 005 and 016.

## Recent-Files Control Removed — Product Evaluation Required

The `save_clock` composer control labeled **Recent files** has been removed from
the visible input area. Its deeper implementation has not been approved for
automatic deletion as part of the fork and clipboard cleanup. The owner needs to
evaluate what, if any, recent-file capability should remain elsewhere in Fusion
Studio going forward.

The removed control currently requests up to 30 files from the active
filesystem-backed panel, recursively scans to a bounded depth, excludes selected
generated/hidden/archive paths, sorts by modification time, and inserts a chosen
panel-relative path into the composer. The server route is
`recent_files_request` / `recent_files_response`, backed by
`file-explorer.js::handleRecentFilesRequest()`.

Before changing that underlying path, evaluate:

- Whether another current or planned surface needs recently changed files.
- Whether this belongs in File Explorer, attachment selection, file
  autocomplete, workspace activity, provenance, or nowhere in the product.
- Whether recursive modification-time scans are an acceptable performance and
  filesystem-trust model.
- Whether `recent_files_request`, its server scan, client module, response types,
  tests, and documentation should be retained with a named owner, moved behind a
  different surface, or removed completely.

Do not silently fold recent-files backend removal into the fork/clipboard work.
Record the owner decision first, then either preserve a tested consumer or remove
the unused path end to end.

## Data And Compatibility

At ticket creation, all Fusion Studio databases found on this machine—including
development and Alpha—contained zero threads with pending or completed fork
metadata. A fork-specific schema migration is therefore not required for the
known local data.

The removal must still fail safely if another installation contains inert
`pendingFork` or `forkProvenance` keys inside `harness_config`. Ordinary threads,
copied conversation history, and already-materialized OpenCode session IDs must
remain readable. Do not delete threads or exchanges as part of this cleanup.

Clipboard history does contain data: the development database has 30
`clipboard_index` rows and Alpha has 1. Full values are stored separately in the
macOS Keychain under account `fusion-studio` and services named `clipboard:<id>`.

Clipboard removal must deliberately and idempotently clean up both sides:

- Delete the app-owned Keychain values corresponding to indexed clipboard IDs.
- Drop `clipboard_index` through a new forward migration.
- Tolerate missing, already-deleted, or locked Keychain entries and provide
  useful diagnostics without blocking application startup forever.
- Never print clipboard values during cleanup.
- Do not delete unrelated Keychain items, secrets, threads, exchanges, composer
  drafts, or ordinary system clipboard contents.

This product direction supersedes the managed-history portions of RCC-0106.
Any remaining copy-action consolidation should target direct system copying only.

## Acceptance Criteria

- No fork control appears in the composer or another active chat surface.
- The client no longer sends `thread:fork` or handles `thread:forked`.
- The server no longer exposes the fork WebSocket operation or fork service.
- OpenCode runtime startup and sending contain no pending-fork or `--fork` path.
- Normal OpenCode session creation, session-ID persistence, resume, send, stop,
  restart, and thread hydration behavior remain intact.
- Fork-specific production code, types, styles, and focused tests are removed.
- Current documentation no longer describes fork as an available thread action;
  archived design material is clearly historical.
- No clipboard-history control appears in the composer or another active UI.
- No renderer startup task reads or monitors the system clipboard.
- No client or server `clipboard:*` protocol, history store, popover/controller,
  handler, backend, Keychain adapter, secret detector, broadcast, or UEB event
  remains active.
- Assistant reply, Chat ID, note, thread-link, wiki-reference, and resource-path
  copy actions still perform ordinary system clipboard writes where applicable,
  without retaining a Fusion history copy.
- Existing clipboard metadata and corresponding app-owned Keychain entries are
  removed through an idempotent, value-redacting cleanup path; unrelated
  Keychain data remains untouched.
- Historical migrations remain available, while a new forward migration removes
  the active `clipboard_index` table.
- Direct typing, native paste, composer insertion APIs used by non-clipboard
  features, and normal chat sending remain intact.
- Clipboard-history production code, styles, message types, redaction entries,
  and focused tests are removed or replaced with direct-copy regression tests.
- No Recent files control appears in the composer.
- The remaining recent-files client/server capability has an explicit owner
  decision: retain/move it with a named consumer and tests, or remove it end to
  end. No dormant request route or recursive scanner is left accidentally.
- Client build and relevant lint checks pass.
- The full server test suite passes, with focused regression coverage for normal
  OpenCode first-send/resume/restart behavior and ordinary direct copy/paste after
  both subsystems are gone.
