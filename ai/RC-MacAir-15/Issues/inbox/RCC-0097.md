`ai/<machine>/Issues/scripts/create-ticket.js` predates the current ticket system shape and is broken on four axes. It is not just unused — the server **wires it into the trigger/automation pipeline at boot**, so any automation that fires a create-ticket action calls the broken code at runtime.

Filed while the ticket system is under construction; this documents the live wiring so the rebuild accounts for it.

---

## How the Script Is Stale

1. **Throws at call time.** `createTicket()` opens with an unguarded `JSON.parse(fs.readFileSync(SYNC_PATH))` — `sync.json` no longer exists, so every invocation throws ENOENT.
2. **Wrong ID convention.** Generates `KIMI-NNNN` IDs; current convention is `RCC-NNNN` (at RCC-0097 as of this ticket).
3. **Wrong destination.** Writes the ticket file to the issues-viewer **root**, not `inbox/` (or any of the state folders: open/closed/complete/archive).
4. **Would corrupt index.json.** The script treats `index.json` as a ticket index and injects a `tickets` map into it — but that file is now the **view metadata** file (version/label/type/icon). If sync.json were restored without fixing this, the first trigger-created ticket would mangle the panel config.

## Live References (the blast radius)

The server wires the script in whenever it exists in the active workspace — in fs-dev it exists, so the boot guard passes and the broken function flows through the whole automation stack:

- `fusion-studio-server/lib/startup.js:250-253` — requires the script at boot, wraps it with the hold registry, injects into action handlers and the cron scheduler. The "ticket creation disabled" fallback only fires when the file is *absent*, not when it's broken.
- `fusion-studio-server/lib/watcher/actions.js` — the `create-ticket` action handler calls `deps.createTicket` (watcher filters → throws at fire time).
- `fusion-studio-server/lib/triggers/trigger-loader.js` — TRIGGERS.md blocks **default** to the `create-ticket` action; also wraps it for auto-hold.
- `fusion-studio-server/lib/triggers/cron-scheduler.js` — cron triggers call `createTicketFn` (wrapped in `runSafely`, so failures are logged rather than crashing).
- `fusion-studio-server/lib/triggers/hold-registry.js` — receives ticket IDs from the startup wrapper; gets nothing while creation is broken.

Net effect today: any TRIGGERS.md automation or watcher filter whose action is (or defaults to) `create-ticket` silently produces no ticket.

## What Needs to Happen

Decide as part of the ticket-system rebuild:

1. **Pick the contract** — what does programmatic ticket creation look like in the new system? (ID allocation source, RCC- prefix, frontmatter shape, lands in `inbox/`.)
2. **Rewrite or retire the script** — either bring `create-ticket.js` up to the new contract, or delete it and move creation into a server lib module so the trigger pipeline doesn't depend on per-workspace scripts.
3. **Fix the boot guard** — `startup.js` should detect a *broken* script (not just a missing one), or the dependency should be inverted per (2).
4. **Keep index.json safe** — whatever the new creation path is, it must not write a `tickets` map into the view metadata file.

## Verification

- Fire a TRIGGERS.md or watcher `create-ticket` action → a correctly numbered RCC ticket appears in `inbox/` with valid frontmatter.
- `index.json` still contains only view metadata afterward.
