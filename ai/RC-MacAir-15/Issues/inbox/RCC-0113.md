## Goal

Define and enforce the process-isolation boundary for Fusion Studio workspace applications that ship executable backend code.

Fusion-owned routers and services may continue to run inside the main Fusion server process. Code supplied by a registered workspace must never be loaded with `require()` or `import()` into that process. A defect, dependency conflict, deliberate process exit, or unhandled rejection in one workspace application must not crash Fusion Studio or another workspace.

## Rule

All workspace-owned Node backend code runs in a Fusion-managed child process.

The distinction is ownership, not whether the workspace is first-party or third-party:

- Fusion repository code may run in the Fusion server process.
- Workspace repository code runs out of process.
- A workspace application may still use Fusion's HTTP origin and navigation shell through an authenticated/restricted proxy owned by Fusion.
- A workspace application owns its domain database, migrations, business rules, and API implementation. It must not add domain tables to `fusion.db` or obtain Fusion's internal database handle.

Do not implement a generic SQL-over-HTTP or arbitrary filesystem API as a shortcut. The child owns its database and exposes domain operations through its own API.

## Proposed Workspace-App Contract

A registered app workspace may declare a backend entry point and local data location in a manifest, for example:

```json
{
  "id": "solobooks",
  "backend": {
    "runtime": "node",
    "entry": "server/fusion-backend.js",
    "healthPath": "/health"
  },
  "frontend": {
    "entry": "app/index.html"
  },
  "data": {
    "database": "data/solobooks.db"
  }
}
```

Manifest field names are provisional; approve the contract before implementation. Paths must be relative, canonicalized, and proven to remain within the registered workspace root. Symlink and traversal policy must follow Fusion's workspace trust rules.

## Managed Lifecycle

Fusion owns orchestration while the workspace child owns domain behavior:

1. Resolve the registered workspace and validate that its type permits an app backend.
2. Validate the manifest and backend path without accepting an arbitrary path from an HTTP or WebSocket request.
3. Spawn the child with an explicit working directory, minimal environment, negotiated loopback port or private IPC transport, and a generated per-launch capability token.
4. Wait for a structured ready/health signal before routing UI requests to the backend.
5. Proxy only the workspace-specific API surface; never expose the child's unrestricted filesystem or Fusion internals.
6. Capture bounded, workspace-attributed stdout/stderr for diagnostics.
7. Detect startup failure, unhealthy state, unexpected exit, and restart loops. Surface a recoverable error in the workspace UI without terminating Fusion.
8. Stop the child on workspace unregister, app disable, Fusion shutdown, or explicit restart. Avoid orphan processes.

Workspace switching alone should not implicitly destroy a healthy child if Fusion's product policy allows background app work. Define idle suspension separately from navigation.

## Database Boundary

Each workspace application opens its own database connection in its child process. For Solobooks, the intended shape is:

```text
<workspace>/data/solobooks.db
```

Requirements:

- The workspace application owns schema migrations and database compatibility.
- `fusion.db` remains the Fusion platform database and workspace registry.
- Fusion's generic machine-scoped `Workspace-db/workspace.db` remains workspace infrastructure rather than an application-domain database.
- Database, WAL, and shared-memory files are excluded from Git unless an explicit export/fixture workflow says otherwise.
- Backup, restore, export, and integrity checks are application responsibilities.
- The child receives only its approved workspace/data paths, not Fusion's internal database path or handle.

## API And Origin Boundary

Prefer a Fusion-owned proxy path such as:

```text
/api/workspaces/:workspaceId/apps/:appId/*
```

The proxy must bind the route to the registered workspace and the exact managed child. It must not trust a caller-provided repository path. Use narrow origin and capability checks so a random local webpage cannot call financial or other private workspace APIs.

If a `fusion-studio://` iframe is used, reconcile the active V2 machine-scoped view path with the Electron protocol handler and provide a deliberate same-origin or narrowly scoped CORS policy. Do not broaden CORS globally to make one workspace app function.

## Crash And Restart Policy

- A child crash must not crash or restart the Fusion server.
- Automatically restart only within a bounded policy, such as a small attempt count with backoff.
- Stop automatic restart after a crash loop and present logs plus an explicit retry action.
- Do not replay non-idempotent requests after an ambiguous child failure.
- Use request or command IDs for operations such as payment receipt, invoice issuance, or other non-idempotent writes.
- A child version or migration failure must fail closed for that app while leaving other workspaces usable.

## Acceptance Criteria

- No workspace-owned backend module is imported into the Fusion server or Electron main process.
- A manifest-backed child can start, report ready, serve a workspace-scoped API, and stop cleanly.
- Workspace paths are resolved only from the authoritative registered workspace and cannot escape its root.
- The child receives a minimal environment and cannot obtain Fusion's internal SQLite handle through the host contract.
- The child uses its own application database and migrations.
- Fusion proxies requests only to the child associated with the requested registered workspace/app pair.
- A child crash leaves Fusion and other workspaces running.
- Startup failure, health failure, crash loop, manual retry, and shutdown have focused tests.
- Fusion shutdown and workspace unregister leave no orphan child process.
- Logs are bounded, attributed, and redact configured secrets/capability tokens.
- Non-idempotent requests are not silently duplicated across retries or restarts.
- Browser/server and Electron integration coverage verifies the proxy, lifecycle, path guards, and crash isolation.

## Non-Goals

- Moving Fusion-owned server modules into child processes.
- Sharing Fusion's Knex instance or adding workspace-domain migrations to `fusion.db`.
- Building a generic raw SQL, arbitrary code, or arbitrary filesystem remote procedure interface.
- Defining cloud multi-user hosting for workspace apps.
- Treating a workspace switch as automatic permission to stop all background work.
