Build the foundation for app-wide event ledger, resource versioning, autosnapshot recovery, and AI edit provenance. This supersedes the Office-only versioning framing and the old local-Git versioning path.

The goal is durable recovery and searchable history even when the user has not committed to Git, the AI has damaged a file, or chat/tool-call history is unavailable after compaction.

## Locked Decisions

- Durable versioning flows through the app event bus, not wire.
- The event bus is the live in-process firehose. A SQLite event ledger is the durable searchable record.
- Internal app SQLite is the canonical store for event ledger rows, autosnapshots, checkpoints, restore metadata, and AI edit provenance.
- The local Electron app database is per-machine and canonical for that machine's ledger/versioning/checkpoint state.
- Repo-local mirrored databases are smaller shareable work product and should FIFO under the configured size cap, currently targeting under 80 MB to avoid GitHub/GitLab issues.
- WebSocket/wire may still be used at the delivery edge while legacy paths exist, but it is not the source of truth.
- RAM undo/redo stays editor-local and fast. SQLite is for durable recovery, not keystroke-level editor history.
- The system is app-wide: Office viewer, doc viewer, file viewer, wiki pages, code files, chat events, workspace events, and agent runs should all use the same event spine with domain-specific subscribers.
- Local machine naming is first-class. On onboarding/download, the user names the machine/app instance (example: `RC-MacAir-15`, `RC-MacMini-Home`).
- The machine name becomes the filesystem namespace under `ai/<machine-name>/`.
- Internal SQLite is per-machine, so durable ledger/versioning rows do not need a stable hardware fingerprint or machine UUID for isolation.
- Store the current given machine name/slug in internal SQLite and keep prior local names/slugs to support repair flows when a workspace still contains `ai/<old-machine-name>/`.
- See RCC-0099 for the provisional machine fingerprint script and manual `system_config` seed shape explored during the AI Workspace Template V2 build. That prototype is useful future onboarding/reinstall-detection context, but it is not approved for this ledger/versioning foundation.

## Target Shape

```text
domain action happens
  -> emit canonical event on event bus
      -> event-ledger subscriber records searchable row
      -> versioning subscriber records autosnapshots/checkpoints when relevant
      -> realtime-refresh broadcaster updates open clients when relevant
      -> trigger subscriber runs optional user-defined automations
      -> domain subscribers update projections/state
```

`TRIGGERS.md` is one subscriber family, not the hub. The event bus is the hub. The event ledger is the durable query surface.

## Terminology

- Workspace, repo, and project folder refer to the same boundary: the root folder the app has opened.
- Views and panels refer to the left-side icon-navigated surfaces inside a workspace/repo.
- A view/panel may display files from different content roots. Versioning, ledger edges, and realtime subscriptions should follow the resolved resource path being displayed, not assume the view folder is the content root.

## Machine Namespace Policy

The revamped AI folder system should store machine-scoped app work under:

```text
ai/
  <machine-name>/
    views/
    wiki/
    tickets/
    workflows/
    state/
    config/
    data/
    chat/
    runs/
```

This allows users and collaborators to push/pull machine-scoped AI state through Git without overwriting one another's setup. A user can inspect another machine's wiki, tickets, workflows, runs, and repo-local databases while keeping their own machine namespace separate.

The canonical internal app database is per-machine. It does not need a hardware fingerprint or globally stable machine UUID to isolate ledger/versioning rows because it should not merge rows from other machines.

The app should register the current local machine display name/slug in internal SQLite and use that slug as the workspace folder namespace. The given name is the user's declared name for this installed app instance.

```text
local_machine
  machine_name
  machine_slug
  created_at
  updated_at

local_machine_name_history
  machine_name
  machine_slug
  first_seen_at
  last_seen_at
```

On workspace/project load, the backend should verify that the current machine slug has a matching repo-local folder:

```text
ai/<machine-slug>/
```

If `ai/<current-machine-slug>/` is missing, the backend should check `local_machine_name_history` for prior slugs that exist under `ai/`. If a prior slug exists, the client should present a repair flow instead of silently creating an empty workspace shell.

Repair copy:

```text
It looks like this project folder was using ai/<old-machine-name>/ to store your view configuration, wikis, issue tickets, and agents. Would you like to rename that folder to ai/<new-machine-name>/?
```

Initial repair actions:

- Rename `ai/<old-machine-name>/` to `ai/<new-machine-name>/`.
- Use the existing name again by switching the local DB value back to `<old-machine-name>`.
- Cancel and leave the workspace unopened.

If `ai/<new-machine-name>/` already exists, do not auto-merge folders. Show a blocked repair state and require a more explicit migration.

A repo-local `machine.json` manifest is optional for this slice. If added, it should store only local display metadata such as name, slug, creation/update timestamp, owner label if known, and schema version. A hardware fingerprint is deferred unless a later onboarding/reinstall-detection ticket makes it necessary.

## Event Ledger Policy

The ledger should be append-only and queryable. For this build, prioritize durable audit of file/resource mutations and checkpoints rather than a broad log of every UI action or read. It should store identity, timing, actor, relationships, tags, and pointers. It should not inline large snapshots, full chat transcripts, or large diffs unless a domain-specific table deliberately stores that detail.

Reads are out of scope for the initial audit ledger. Mutations are in scope:

- File content changed.
- File created.
- File deleted.
- File renamed.
- File moved to another folder/path.
- Folder created.
- Folder deleted, including empty folders.
- Folder renamed/moved.
- Checkpoint created.
- Restore committed.
- Before a restore rewrites a resource, create a `before_restore` checkpoint attributed to the initiating actor: human or assistant.

For AI-initiated mutations, ledger rows should link to the chat/thread id when available, the AI run/tool metadata when available, and the relevant checkpoint ids. Agent runs should record a completed-run summary and the files affected; if no files changed, record that outcome on the run record. Ticket and wiki edits do not need special handling in the ledger because they are file mutations and should be captured through the same resource path mechanism.

Logical tables:

```text
event_log
  event_id
  event_type
  workspace_id
  actor_type
  actor_id
  occurred_at
  summary
  payload_json
  source_module
  correlation_id
  causation_id

event_resource_edges
  event_id
  resource_type
  resource_id
  workspace_id
  path
  resource_name
  parent_path
  role

event_tags
  event_id
  tag
```

Domain detail should live in tables such as `resource_versions`, `resource_checkpoints`, `chat_exchanges`, `agent_runs`, `tool_calls`, and `workspace_sessions`, linked back through event ids and resource edges.

## Autosnapshot Policy

Autosnapshots are hidden by default and exist for crash recovery.

- When a resource becomes dirty, start an active edit session.
- After 5 seconds of no edits, write an autosnapshot if the content hash changed.
- While a resource remains continuously dirty, write an autosnapshot at most every 60 seconds even if there is no long pause.
- Keep the last 30 autosnapshots per resource for recent recovery.
- Promote every 20 autosnapshots into a checkpoint when content changed and no equivalent checkpoint already exists.
- Autosnapshots should not replace editor-native RAM undo/redo.

## Checkpoint Policy

Checkpoints are visible recovery points.

- Create a checkpoint when a file tab/resource is closed.
- Create a checkpoint when navigating away from a file/resource in any form.
- Create checkpoints on workspace switch for dirty or recently active resources.
- Create manual checkpoints/save milestones when the UI exposes that action.
- Promote every 20 autosnapshots to a checkpoint so long editing sessions keep durable milestones beyond the short autosnapshot tail.

## AI Edit Policy

AI edits are always durable and inspectable.

- Any file/folder change that originates from a chat turn counts as an assistant-originated mutation.
- Use simple chat-turn attribution: resource mutations between the user request/turn start and turn end are linked to that chat/thread/turn.
- Do not duplicate detailed tool-call data in the resource ledger. Tool calls already live in the chat log; the resource ledger only needs enough chat/thread/turn identifiers to find the original thread for forensic review.
- Before applying an AI file edit, record a checkpoint.
- Apply the edit through the same app mutation/event-bus pipeline used by user edits.
- After the edit is applied, record the after checkpoint/version.
- Link AI checkpoints to available AI metadata: run id, thread id, tool call id, actor, timestamp, before hash, after hash, and diff/snapshot references.
- Preserve AI checkpoints indefinitely in the canonical per-machine Electron DB.

## Retention Policy

- Keep recent human autosnapshots/checkpoints in detail.
- After 72 hours, collapse human history to the last human checkpoint per file per day.
- Preserve all AI checkpoints indefinitely in the canonical per-machine Electron DB.
- Preserve manual checkpoints unless explicitly deleted.
- Autosnapshot/checkpoint retention is local-app-instance-specific. The canonical internal DB should only prune its own recovery tail.
- Retention should be activity-driven per resource. When new checkpoints are created for a resource, asynchronously clean older eligible full-day human checkpoint clusters for that same workspace/resource/machine.
- Do not churn dormant resources just because the app is running 24/7. If a file has not been touched in months, cleanup can wait until the resource receives a newer checkpoint or an explicit maintenance job runs.
- Only collapse a full day of human checkpoints when there is a later checkpoint for that resource. Example: Jan 1 has 7 checkpoints, Feb 23 has 8 more, March 1 work resumes; March 1 activity can collapse Jan 1 to that day's last human checkpoint.

### Slice 1 - Local Machine Folder Integrity

Goal: Resolve the current local machine name before durable ledger/versioning work and ensure the active workspace has the matching `ai/<machine-name>/` folder.

Scope:
- Add or revise internal SQLite local machine config tables for current given name/slug and prior names/slugs.
- Add a local machine resolver service.
- During onboarding or first-run fallback, create/select the current local machine name.
- On workspace/project load, require `ai/<machine-name>/` to exist before showing workspace views/content.

- Do not add a hardware fingerprint for this slice.
- Do not require a stable machine UUID in ledger rows for this slice.
- Expose a minimal diagnostic endpoint or server log showing the current local machine name and slug.

Smoke test:

- Opening a workspace without matching `ai/<machine-name>/` blocks view/content loading.
- If a prior machine-name folder exists, the app offers a repair state instead of silently creating a new empty folder.
- If both old and new machine-name folders exist, no automatic merge occurs.

## Assumptions To Review

- Local machine name/folder integrity is required before any durable ledger/versioning write for a workspace resource.
- Current app-internal SQLite (`fusion.db`) is the canonical store for the ledger and recovery metadata.
- Repo-local per-machine SQLite mirrors are optional work product, not canonical state.
- The first autosnapshot implementation should start with one editor/resource path before broadening app-wide.
- The event ledger should store metadata and pointers, not large blobs by default.
- Resource snapshots/diffs may live in resource-specific tables or external refs, linked from the ledger.
- `resource:*` events should replace older `file_changed`/`file:changed` paths as the canonical server-side resource mutation event family.
- Resource mutation events should include resource type, resource name, and location/path at the time of change.
- Chokidar/external filesystem watcher changes are in scope for the ledger and recovery pipeline.
- Actor/source classification should distinguish the current local user, assistant, agent-run, and system/script automation.
- Critical recovery behavior should not depend on `TRIGGERS.md`; triggers remain optional automation subscribers.
- Button clicks should generally be represented as semantic action events, not raw click telemetry.
- Realtime external/assistant updates should override open dirty editor state by default. Before overriding, save a recoverable snapshot/checkpoint of the local dirty state.
- Subscriptions/versioning should key off the resolved resource path that a view is displaying, not the view folder itself. File viewer may display repo-root files; doc/office viewers may display `ai/<machine-name>/docs` or `ai/<machine-name>/office`; view folders may only hold state/styles.
- Machine rename is deferred to a chat-driven workflow. Direct panel edit buttons should preload the rename workflow into chat rather than mutating DB/folders inline.
