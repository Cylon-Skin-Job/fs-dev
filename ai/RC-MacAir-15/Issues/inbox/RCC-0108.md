Design and implement the chat UI behavior for provider thinking blocks that exist structurally but have no renderable text.

## Problem

OpenCode can emit `type: reasoning` events for some providers where `part.text` is empty and the useful reasoning payload is opaque or encrypted metadata. In the observed OpenAI-backed path, reasoning tokens existed and `metadata.openai.reasoningEncryptedContent` existed, but there was no visible thinking text for Fusion to render.

That creates a bad live UX: the user may stare at an orb or empty thinking affordance while the model is working, then end up with an empty dropdown after final text renders.

By contrast, Kimi Code 2.7 through OpenCode emits non-empty `reasoning.part.text`, which should continue to render as a normal visible thinking block/dropdown.

## Target Behavior

- Treat `thinking enabled` and `thinking renderable` as separate runtime states.
- If a thinking/reasoning event arrives with empty text, do not show an empty dropdown.
- While the assistant turn is active and only opaque/empty thinking is available, show a compact activity ticker instead.
- Ticker should show elapsed seconds since opaque thinking began.
- Ticker should show streamed token count if a reliable live token count is available.
- If live token count is not available until `step_finish`, show elapsed seconds only.
- If non-empty thinking text later arrives in the same turn, replace/upgrade the ticker into the normal thinking block/dropdown.
- If assistant text or tool output arrives before any non-empty thinking text, transition cleanly into normal live rendering.
- On turn completion, if no non-empty thinking text ever arrived, remove/collapse the empty thinking block entirely and render only the final text/tools.
- Stop/interrupted turns should follow the same rule: no empty thinking dropdown remains after finalization.

## Implementation Notes

- This is a renderer/state-machine problem first; do not treat it as a provider parser failure.
- The harness translator should continue to preserve non-empty thinking text for models that expose it.
- Empty thinking segments should not create a permanent visible chat artifact unless needed for debugging.
- If persistence currently stores empty thinking parts, decide whether to filter them before saving or hide them during render. Prefer preserving enough metadata for diagnostics without exposing blank UI.
- The UI state should support three distinct cases:
  - no thinking seen
  - opaque/empty thinking in progress
  - renderable thinking text present
- Avoid model-specific hardcoding in the renderer. The renderer should respond to whether text is present and whether the turn is still active.

## Acceptance Criteria

- OpenAI-backed OpenCode reasoning with empty `part.text` shows activity feedback during the live turn instead of a blank thinking dropdown.
- The activity feedback includes elapsed seconds.
- The activity feedback includes token count when live token information exists.
- Completed turns with only empty thinking do not leave an empty thinking block/dropdown in chat history.
- Kimi Code 2.7 reasoning with non-empty `part.text` still renders as visible thinking text.
- Text/tool rendering starts as soon as renderable text/tool events arrive; it is not blocked by an empty thinking block.
- Stop/interrupted partial turns do not leave empty thinking artifacts.
- Smoke tests cover empty thinking, delayed text after empty thinking, visible thinking, and interrupted empty thinking.

### Delivered behavior

- Each accepted prompt owns an immutable route context, unique `drainId`, and
  exact runtime/harness control. Every later mutation, Stop, terminalization,
  and cleanup is compare-checked against the bound drain and server `turnId`.
- OpenCode step-start signals become provider-neutral `step_begin`. The server
  owns the full-turn seen ledger, transient activity/cursor/revision, blank
  initial output suppression, and the sole whole-turn `streamSeq` frontier.
- The client gates every live frame by explicit thread/turn/sequence, installs
  snapshots as already-revealed baselines, drains only contiguous newer frames,
  and isolates tool/grouping/subagent/frontier state per thread and turn.
- The live UI shows the existing small hourglass with truthful
  `Working… Ns`, after orb disposal and queued output. It clears on the first
  renderable thinking/text/tool event, supports post-tool steps, preserves the
  original start time on return, announces one stable status, and respects
  reduced motion. Working never enters segments, parts, SQLite, or history.
- Accepted failed turns preserve and immediately reveal partial output, then
  render exactly one fixed-safe inline error before reply chrome. Snapshot,
  save acknowledgement, and history hydration merge without duplicate rows,
  content, or alerts. Pre-begin/unscoped failures create no transcript error.
- View, Copy, and Ask AI exist only with a valid opaque diagnostic ID. Retrieval
  is explicit, exact-owner, bounded, and validated; Ask AI appends the redacted
  report to the exact composer owner for review and never sends. Central logging
  removes every report field before browser/captured-log forwarding. Copy
  delegates the validated formatted report through the chat controller to
  `writeAndRecord(text, 'chat-diagnostic')`, producing exactly one OS clipboard
  write and one `clipboard:append` history request per activation.
- Composer draft, pending acceptance, retry text, attachments, and async
  screenshot attachment use exact workspace/thread ownership; late activity
  for one owner cannot mutate another.
