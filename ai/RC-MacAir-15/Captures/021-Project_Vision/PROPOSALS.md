# PROPOSALS — Project Vision

> Candidate mechanisms from RC's Project Vision blurt. These records preserve possibilities without claiming owner approval or implementation authority.

## Consent and Trust

### P-001 — Offer semantic capability escalation

- **Category:** consent
- **Status:** superseded
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-001, I-002, I-004

This proposed per-capability or schema-style prompt was superseded by D-016 and D-017. Robin offers to investigate the subject more deeply; accepting that offer establishes durable-recall intent for the subject without asking the user to design memory internals.

### P-002 — Run an observable historical catch-up followed by incremental enrichment

- **Category:** memory
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-007

Process a user-approved historical window in an overnight or long-running job, then transition to incremental triggers. Preserve manifests, changes, failures, and reviewable outcomes.

## Memory and Retrieval

### P-003 — Use modular domain capabilities over a stable platform kernel

- **Category:** modularity
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-006

Let bookkeeping, expenses, CRM, invoices, Docs, email, calendar, code tasks, research libraries, and other capabilities own bounded contracts and migrations while sharing a stable core.

### P-004 — Combine a bounded hierarchy with graph edges

- **Category:** memory
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-005, I-008

Use a database-backed Launchpad container as the substantive topic or entity node. Organize its internal subnodes hierarchically, retain links to raw records, and add cross-cutting semantic edges among maintained nodes for associative traversal.

### P-005 — Promote conversationally reused knowledge into fast recall

- **Category:** memory
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-008, I-009

Increase the short-term salience of information that had to be retrieved and then became part of a new conversation. Refresh the same subject node when it recurs while retaining source links and allowing later decay or demotion.

### P-006 — Attach cognitive-domain metadata to chat pairs

- **Category:** memory
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-005, I-008

Recover the prior cognitive-domain schema and evaluate metadata such as refine/define/shape, brainstorm/ideate, analyze/research, and ponder/imagine/philosophize as one lens for indexing conversations.

### P-007 — Use staged hybrid retrieval

- **Category:** retrieval
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-008, I-009

Query fast indexes, summaries, and graph awareness first; escalate to raw-source inspection, recursive language-model lookup, or high-throughput inference only when the context gap and consent boundary justify it.

### P-008 — Assemble missing context through bounded background agents

- **Category:** coordination
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-008, I-009

Let a fronting assistant complete a broad first pass and remain responsive. When the user asks for deeper investigation, seed bounded background agents with that search and conversation so they can retrieve grounded sources, compare records, and reconcile the result into the subject's durable node.

### P-011 — Use schema-governed containers for personal Wiki maintenance

- **Category:** memory
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-005, I-008

Represent the Launchpad and Second Brain pattern—schema metadata, authority boundaries, update instructions, background work, provenance, and validation—as a reusable database-backed memory node rather than a literal folder. Let topic-specific structures emerge inside the node as it grows.

## System Manager and Coordination

### P-009 — Give Robin a configurable notification and review layer

- **Category:** system_manager
- **Status:** proposed
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-012

Use a bird-icon badge and review surface for cross-workspace events such as modified skills or scripts. Support dismissal, bundling, redirecting, per-workspace silence, timed silence, permanent suppression, and badge thresholds.

### P-010 — Offer an inspectable personal profile and entity timeline

- **Category:** memory
- **Status:** superseded
- **Source:** RC's Project Vision blurt; CAP-012
- **Addresses:** I-001, I-004, I-005

The separate profile-setup prompt was superseded by D-016 through D-018. Users instead receive a place to inspect source-linked, correctable topic and entity nodes whose internal structure is the database form of the Launchpad container pattern.

## Workflow and Ticketing

### P-012 — Create schema-governed Wiki ticket containers

- **Category:** workflow
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-014

When code merges without corresponding Wiki updates, create a folder-shaped ticket container. Let the first AI hydrate it from the change and current documentation before handing a bounded edit to a Wiki specialist and checklist-driven orchestrator.

### P-013 — Support AFK and in-the-loop ticket execution

- **Category:** workflow
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-015

Run pre-authorized ticket stages autonomously while allowing the user to open the same ticket, answer remaining issues, and resume validation from a shared checkpoint.

### P-014 — Let fronting agents propose tickets and delegate bounded work

- **Category:** workflow
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-014, I-015

Allow a fronting assistant to recognize durable work, explain and create the ticket within user authority, delegate independent assignments, and keep the user engaged at stage boundaries.

## Apps and Surfaces

### P-015 — Define one portable app and view host contract

- **Category:** interaction
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-017

Share domain state, commands, events, and components while allowing one capability to render as a web/mobile app, Robin overlay, or desktop workspace view.

### P-016 — Create Personal Inventory as a memory-node browser

- **Category:** app
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-005, I-008

Give users a visually distinctive place to inspect database-backed Launchpad containers for topics, entities, projects, and other subjects. Expose their internal branches, sources, updates, and corrections while also showing useful graph edges among the maintained nodes and underlying records.

### P-017 — Create Weekly Review as a script-backed app

- **Category:** app
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-007, I-012

Generate a recurring checklist from templates, heuristics, and actual data; delegate safe checks; preserve completion and deferral history; and surface exceptional items for discussion.

### P-018 — Define explicit shared-data capabilities for apps

- **Category:** interaction
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-018

Let apps and views share internal database objects only through declared read, write, event, workspace, user, and sensitive-data capabilities with provenance for AI mutations.

## Agent Ecosystem

### P-019 — Package workers as active and inactive templates

- **Category:** agent
- **Status:** proposed
- **Source:** RC's Project Vision continuation; CAP-017
- **Addresses:** I-016

Represent background workers as discoverable templates declaring tools, triggers, scope, confidence, output, and compatible container kinds. Support download, activation, in-place modification, versioning, review, and rollback.

## Routines

### P-020 — Use a companion-style conversational routine runner

- **Category:** interaction
- **Status:** proposed
- **Source:** RC's morning routine example; CAP-027
- **Addresses:** I-022

Guide the user through steps semantically and conversationally, supporting acknowledgement, skip, defer, reorder, clarify, pause, resume, and branches while distinguishing user-reported completion from verification or inference.

### P-021 — Resolve semantic routine aliases through a context-receipt workflow

- **Category:** workflow
- **Status:** proposed
- **Source:** RC's “Status” example; CAP-027
- **Addresses:** I-020

Resolve phrases such as “Status” to a routine node, load its schema, heuristics, attachments, and prior state, identify missing context, create bounded receipts for background workers, wait or report progress, then reconcile their results before replying.

### P-022 — Separate routine orchestration from domain-owned records

- **Category:** modularity
- **Status:** proposed
- **Source:** RC's vitamin, hydration, calendar, app, API, and script examples; CAP-027
- **Addresses:** I-018, I-021, I-022

Let the routine own its instructions, capabilities, run history, and references while domain apps own canonical records such as vitamin intake, hydration, calendar events, and flashcard performance. Preserve every tool call, script result, projection, and correction with provenance.

### P-023 — Refine routines from approved conversation and run history

- **Category:** agent
- **Status:** proposed
- **Source:** RC's background routine-refinement direction; CAP-027
- **Addresses:** I-023

Let bounded background processes compare the maintained routine against approved conversations and prior runs, identify friction or changed intent, maintain questions and future suggestions, and propose or apply changes according to declared authority.

### P-024 — Make flashcard updates an adaptive stateful routine

- **Category:** app
- **Status:** proposed
- **Source:** RC's coding flashcard example; CAP-027
- **Addresses:** I-008, I-022

Track concepts the user struggled with, prior explanations, current cards, practice performance, adaptation speed, and a continually maintained queue of future cards so “update my flash cards” can add, defer, or revise material from grounded context.

### P-025 — Give routine automation separate capability levels

- **Category:** consent
- **Status:** proposed
- **Source:** RC's opt-in auto-update direction; CAP-027
- **Addresses:** I-023

Separate automatic context refresh, improvement suggestions, approved definition changes, next-run preparation, scheduled conversational invocation, and autonomous app actions so users can enable only the behavior they intend.

### P-026 — Run a conditional heartbeat while supervised work is active

- **Category:** workflow
- **Status:** proposed
- **Source:** RC's build and orchestrator supervision idea; CAP-032
- **Addresses:** I-024

Keep the supervisory routine dormant when no watched work is active. While builds or orchestrators are running, wake on a configurable heartbeat, inspect authoritative run state, and proactively report only material progress, failures, stalls, questions, or completions through Robin.

### P-027 — Relay owner answers and continue the originating run through Robin

- **Category:** interaction
- **Status:** proposed
- **Source:** RC's System Manager intervention idea; CAP-032
- **Addresses:** I-025, I-026

Present an orchestrator's exact blocked question in Robin with source and run identity, attach the user's response as owner-authored input, deliver it to the originating checkpoint, and perform the explicitly selected resume, retry, restart, or worker-replacement operation without losing the audit trail.
