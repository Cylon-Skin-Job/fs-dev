Fusion Studio · foundation layer

Style begins with relationships.

A visual and behavioral guide built from first principles downward. We establish semantic roles, geometry, spacing, and state before naming reusable components.

Owner direction Current observation Open decision
01 / Foundation

First principles

Rules describe what an element means and how it relates to its neighbors—not merely what class happens to style it today.

01

Semantics before selectors

Elements may use different structural classes while belonging to the same visual role through a shared semantic variable.

02

Patterns include relationships

A component pattern includes its size, spacing, edge alignment, state, and relationship to adjacent elements.

03

Exceptions remain narrow

An exception belongs to a named context. It does not silently redefine the default used everywhere else.

Current observation

The source selector's hover only recolors its existing 1px border and text; it does not add a CSS outline. Keyboard focus adds a separate 2px outline. The composer uses --glass-sm at 6% white. Capture uses --glass-md at 8% white. File tabs use the content Accent fill, so their effect is visually related but not token-identical.

Owner direction: one interaction system, two visual families

Surface controls shade

Dropdown triggers and view tabs share the Interactive Surface hover fill. The current source-selector border-only hover and the differing 6%/8% fills are replaced by one semantic hover token.

--interactive-hover-bg

Icon-only chrome changes color

Left-rail icons and header icons do not acquire a hover tile. They move from Workspace Foreground to Workspace Accent while their background remains transparent.

03 / Control geometry

The interactive envelope

Hover is only the state. The reusable pattern is the complete area around the content: height, inset, internal gap, radius, and overflow behavior.

Proposed compact envelope Baseline measurements
▤ A deliberately long control or document name × 32px high 8px inset 8px radius 18px fade
Geometry stays fixed The background envelope owns a 32px height, 8px inline padding, 8px corners, and a 6px content gap.
Capacity may respond A tab, machine selector, or menu item may receive a different label width without changing the space around its content.
Overflow stays predictable One-line labels clip through a right-edge fade. A trailing action receives a reserved well rather than compressing the outer padding.
Owner direction: background geometry is part of the component contract

Uniform envelope

Controls should present the same amount of background above, below, and beside comparable text. Hover, open, and selected states fill the same physical envelope.

--interactive-control-*

Tabs are responsive, not exempt

Tabs may shrink their label well and reveal an overlaid close action, but the outer height, inset, corner shape, and fade behavior still come from the shared contract.

--interactive-label-*
◫
Left navigation rail exception

The left-sidebar icon targets belong to the navigation rail's own geometry: currently a 40px square target with a 24px glyph. They retain a transparent background and change from Workspace Foreground to Workspace Accent on hover. They do not inherit the compact text-control padding, radius, or 32px envelope.

Current observation

Capture currently caps its label at 16ch and uses ellipsis. Files caps each tab at 140px, fades the final 18px, and expands the action fade to 24px in compact mode. Compact controls currently vary between 28–32px high, 6–10px inline padding, and several radii.

Open: confirm the baseline numbers

The illustrated starting point is 32px height, 8px inline padding, 8px radius, 6px internal gap, and an 18px label fade. The principle is owner direction; these exact measurements remain proposed until confirmed.

Owner direction: dropdowns and context menus share one themed contract

Navigation-derived shell

Menu Background aliases Navigation Background. The outer border aliases Navigation Foreground. These are currently exposed in code as the Side Panel surface and foreground tokens.

--menu-surface-bg: var(--side-panel-surface-bg) --menu-border-color: var(--side-panel-foreground-color)

High-contrast contents

Normal labels, icons, shortcuts, and internal dividers are white in dark mode and black in light mode. Delete alone uses the destructive error color. Hover uses the shared Interactive Surface treatment.

--menu-foreground-color --status-error

Common action catalog

A single catalog defines stable action IDs, labels, Material icons, and semantic tones. Initial entries include Open, Rename, Make a Copy, Duplicate, Star/Unstar, Pin/Unpin, Archive/Restore, and Delete.

COMMON_MENU_ACTIONS

Menu composition

A view references catalog entries, chooses their order and groups, and supplies runtime state: visible, enabled, current, and the action callback.

menuAction('rename', { onSelect })

Shared renderer

The renderer owns the menu surface, placement, row envelope, icons, dividers, hover, focus, submenus, dismissal, and keyboard navigation.

MenuSurface

Specialized actions

Office table commands and other domain-specific items may define local descriptors, but they still render through the same surface and item contract.

MenuActionDescriptor
Current observation

Capture and Office tile ellipses already open the same programmatic showContextMenu renderer, but they compose actions separately: Capture provides icons while Office's shared file/folder hook currently does not. Other dropdown and Office editor menus still use separate surfaces, tokens, and row implementations.

Owner direction: icons are required

Every actionable row has an icon

The catalog supplies the canonical icon so Rename, Archive, Delete, and other common actions do not drift between views.

icon

Variant pairs stay related

Star/Unstar, Pin/Unpin, and Archive/Restore are state variants of one conceptual action and retain coordinated labels and icons.

05 / Color

Workspace color roles

The Workspace Settings sliders control semantic groups, not one universal CSS class.

Foreground

Normal workspace chrome

Header text, the workspace name, ordinary header icons and navigation buttons, left-rail view icons that are neither hovered nor selected, and inactive view-tab labels and icons.

--workspace-foreground-color
Accent

State that must stand apart

The Connected indicator; hovered header and left-rail icons; the currently selected view icon; and the active view-tab treatment. Hover and selection temporarily override the normal Foreground role.

--workspace-accent-color

09 / Unresolved

Open questions

Unsettled details stay visible rather than being filled in by assumption.

Menu catalog migration

Inventory specialized and repeated menu commands, then decide which enter the common catalog first during renderer convergence.

Interactive-envelope values

Confirm or revise the proposed 32px height, 8px inline inset, 8px radius, 6px content gap, and 18px right-edge fade. The left navigation rail is explicitly outside this envelope.

View-tab background

Which semantic surface becomes canonical when the tab header is shared across all views?

Interaction states

The shared hover families are now defined. Focus, disconnected, pressed, and selection-marker treatments still need their complete state rules.
