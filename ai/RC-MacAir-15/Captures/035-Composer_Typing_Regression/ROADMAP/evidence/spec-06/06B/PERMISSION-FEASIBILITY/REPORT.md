# OpenCode1.18.32 pending-permission feasibility (read-only)

Conclusion: supported approval-and-continuation exists through the headless server's SDK/HTTP permission API. Existing `opencode run --format json` cannot be made interactive by piping an approval to stdin. No product/config/runtime changes, process launches, provider calls, live-app reads/input/restarts, dependency downloads or permission-policy changes were performed. Only official source research/evidence files were written. The particular permission involved in the observed bash error remains unknown.

## Exact-version findings

All source URLs below are pinned to https://raw.githubusercontent.com/anomalyco/opencode/v1.18.32/ ; complete fetched files and SHA256 receipts are in packages/ and sources.json.

1. **CLI run is deliberately noninteractive.** `packages/opencode/src/cli/cmd/run.ts:416–418` reads non-TTY stdin to EOF as prompt text. It is not a duplex permission protocol. `:801–819` handles permission.asked for its session/descendants by replying reject unless auto mode is set (then once). The JSON branch does not provide a pending approval control channel. `--attach` invokes that same execute loop (`:943–945`), so a serve process plus run--attach still races to reject. `--mini` has terminal permission UI but is incompatible with JSON and requires TTY stdout/controlling terminal (`:304–320`, runtime.stdin.ts); automating that UI would replace the protocol, not repair this structured integration. Do not use --auto or pipe “yes”.

2. **Use the existing V1-compatible API surface directly.** `server/routes/instance/httpapi/groups/permission.ts`: GET `/permission` lists pending requests in the routed directory/instance; POST `/permission/:requestID/reply` with `{reply:'once'|'always'|'reject', message?:string}` returns200 boolean; bad request400, missing/already-consumed404. SDK `packages/sdk/js/src/v2/gen/sdk.gen.ts:3085–3155` exposes `client.permission.list/reply`, with directory/workspace routing. Despite SDK package path v2, these are the existing V1-compatible endpoints. New `/api/session/.../permission` surfaces also coexist in generated source; do not accidentally mix their types/semantics into this migration.

3. **Pending event carries real provenance.** `packages/schema/src/v1/permission.ts:27–36,61–67`: request `{id,sessionID,permission,patterns:string[],metadata:Record<string,unknown>,always:string[],tool?:{messageID,callID}}`; `permission.asked` carries that request, `permission.replied` carries sessionID/requestID/reply. These supplied fields—not the eventual generic tool error—identify requested permission/operation. Metadata is arbitrary; normalize bounded safe fields before exposing it through Fusion's canonical boundary. Subscribe GET `/event` before sending prompt, then list pending requests to reconcile subscription/reconnection races. List covers every session in that instance: Fusion must validate exact provider session/request against its own thread/turn/generation.

4. **Reply resumes the waiting operation.** `packages/opencode/src/permission/index.ts:86–106` stores a Deferred in pending and suspends the tool; `:109–143` removes the request, publishes replied and succeeds the Deferred for once. This resumes the original tool/turn without resending the prompt. Reject fails it with RejectedError, or CorrectedError when a message exists, and rejects *all other pending requests of that same provider session* (`:121–139`). This is stronger than “reject only this card.” Missing IDs fail, not silently succeed; duplicate/lost-ACK retries require reconciliation rather than treating404 as permission granted or resubmitting prompt.

5. **“Always” has wider runtime scope than a thread.** `permission/index.ts:145–166` adds tool-supplied `always` patterns to in-memory approved rules. InstanceState is keyed by directory (`effect/instance-state.ts:26–54`), not sessionID. Future requests in another session under that same directory instance can use those approvals; pending requests in other sessions are *not* proactively released. Upstream test `test/permission/next.test.ts:777–805` explicitly approves in session_test then allows a matching ask in session_test2; `:878–907` keeps an already pending different-session request pending. No disk persistence is written by this owner; disposal/restart loses the memory. UI `cli/cmd/run/permission.shared.ts:128–138` says until OpenCode is restarted. Public docs' wording “current OpenCode session” is less precise than source. Do not label it thread-only or permanent. Once/reject is the narrowest first implementation; whether/how to offer always is a real scope choice for root/owner.

6. **Reconnect is not resume of a destroyed pending operation.** SSE handler `server/routes/instance/httpapi/handlers/event.ts:26–78` installs a live event subscription, emits server.connected/heartbeat, unregisters on close, and does not replay prior requests. No Last-Event-ID replay is implemented there (SSE id itself is undefined; payload has event ID). A network disconnect alone does not clear the permission map; GET /permission recovers pending state while the same instance survives. Instance finalization rejects and clears pending (`permission/index.ts:54–61`), and an interrupted ask removes itself in ensuring (`:101–106`). Pending waits/approval memory are not durably recreated by resuming saved provider transcript after server death. Do not offer a stale approval that claims to continue a terminated operation.

7. **Supported Stop is session abort, with boundedness still to test.** POST `/session/:sessionID/abort` calls promptSvc.cancel (`handlers/session.ts:232–235`); SessionRunState cancels background jobs belonging to that session/descendants then that session runner (`session/run-state.ts:77–85,111–141`). Runner cancel interrupts/awaits its fiber (`effect/runner.ts:171–180`); permission ask ensuring removes pending, processor finalizers mark abandoned tools interrupted. This is a source-supported cancellation path, not a measured 3s guarantee. No undo of an already approved/executing side effect is promised. Fusion must retain existing Stop grace/iterator/retirement bounds and test approve-vs-Stop races, stale replies and no peer stop. Killing a shared server would affect peer sessions, so it cannot be the ordinary Stop substitute.

## Minimal executable direction to take for approval

Recommendation: migrate the OpenCode adapter's per-turn JSON subprocess transport to an owned `opencode serve` connection using direct SDK/HTTP prompt/events/permission.reply. Preserve canonical Fusion prompt acceptance, thread/turn routing, Stop and saved delivery; represent pending approval as still-running/waiting instead of turn completion. Do not keep a `run --attach` consumer for the same turn. This is substantive adapter/transport integration, not an error-only UI patch.

Service setup needs explicit loopback/ephemeral port/no mDNS and generated process-local server authentication. `cli/network.ts:62–79` shows config can override defaults, so pass explicit flags. `server/auth.ts` uses OPENCODE_SERVER_PASSWORD/USERNAME (Basic auth); current Fusion closed env does not pass these, so implementation would need narrowly owned generated values, never broad host inheritance or renderer exposure. Preserve model/provider/variant/thinking selection and existing OpenCode config/Claude-disable policy. Prompt_async forks work into service scope and returns204 (`handlers/session.ts:311–328`); subscribe/reconcile and correlate session/message/turn rather than treating204 as completion. Existing sync prompt also works if event/reply handling runs concurrently.

Runtime ownership options: one service per existing Fusion provider-session lifetime best contains peer Stop/failure/approval-memory effects, at process cost; shared service per workspace can reduce processes but requires deliberate peer-safe retirement plus truthful always scope. Do not choose a global shared lifetime solely to make permissions work. Root owns final scope decisions. Transport switch can reuse a known persisted provider sessionID under the same OpenCode data roots for history, but cannot revive the already rejected/terminated tool call. Need a new user-authorized turn to retry that operation; never silently replay an uncertain tool invocation.

Keep current deny/policy behavior unchanged. Noninteractive run currently adds deny rules for question/plan_enter/plan_exit (`run.ts:430–448`); direct API bypasses that CLI policy insertion, so migration must explicitly retain it or route this separate capability difference for owner decision. `--thinking` in CLI controls visible output; preserve actual provider reasoning configuration independently when mapping to API.

## Required tests before claiming done

- Real isolated harmless tool ask: no tool side effect before approval; pending card actual permission/patterns; once reply executes original tool once and same turn continues to actual assistant finish/saved outcome.
- Reject/feedback and concurrent pending requests: truthful same-session cancellation; peer session remains untouched. No tool-calls finish mistaken for successful completion.
- Reply identity/generation/thread/turn/call validation; malformed/wrong-session/wrong-directory/forged/stale/duplicate replies; request IDs that disappear with uncertain HTTP ACK; no automatic resend or duplicate tool work.
- Reconnect while pending: subscribe+list reconciliation deduplicates; no lost pending request, no plaintext auth leak, no peer cards. Event stream loss is not idle or successful turn completion.
- Stop/Delete/workspace retirement before approval, approval/Stop race, server death/respawn, exact owned cleanup and existing timing bounds; never approve after cancellation or kill an unrelated peer.
- If always is exposed: exact tool patterns, future same-directory peer behavior, pending-peer distinction, disposal/restart forgetting, deny-rule interactions, explicit truthful user scope.
- Prompt/command/session reuse, model/high/thinking/config/secret isolation, question/plan policy parity; ordinary nonpermission turns and stream/final/error/Stop regressions.
- Real owned isolated runtime validation plus UI/public-route tests required; this feasibility report ran no inference, permission action or runtime test.
