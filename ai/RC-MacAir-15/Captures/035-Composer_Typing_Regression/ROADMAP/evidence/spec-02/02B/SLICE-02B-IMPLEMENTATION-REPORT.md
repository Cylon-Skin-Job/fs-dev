Chosen authenticated session action: `thread:action` `{type:'thread:action', action:'prompt_receipt_status', requestId, threadId}`. The existing trusted-shell guard and bound workspace provide authority. The action accepts exactly those four keys. A committed response is `{type:'thread:action:completed', action:'prompt_receipt_status', requestId, workspaceId, threadId, receipt:{workspaceId,threadId,requestId,outcome,execution,turnId,reason,content?}}`; `content` is included only for accepted receipts and is the accepted snapshot for exact ACK reconstruction. `outcome` is `reserved|accepted|rejected|cancelled`. `execution` is `not_dispatched` while accepted and awaiting claim, `failed_before_dispatch` with a bounded reason after a known post-commit failure, `interrupted_before_dispatch` after startup finds an accepted/unclaimed row, or `unknown_after_dispatch_claim` after the durable claim. A status query with no receipt creates a durable `cancelled` tombstone (`reason:'recovery_fence'`); it never sends an unfenced not-found. Invalid/foreign targets return bounded `thread:action:error`. A same-key prompt replay returns the original `message:sent` with exact `workspaceId`, `threadId`, `requestId`, `turnId`, and `content`; a mismatched snapshot returns a correlated `error` with `code:'request_mismatch'` and does not change the original attempt.

Post-commit execution failure wire shape for 02C: `{type:'error',scope:'project',workspaceId,threadId,requestId,recoverable:true,code:'accepted_execution_failed',message:'Accepted prompt could not start'}` for helper/activation/drain/claim failure. A provider failure companion retains its existing fixed safe message and adds `code:'accepted_execution_failed'`. If its `message:sent` ACK is lost, the client marks the attempt `unknown` and keeps resend gated. 02C must recover this exact request via `prompt_receipt_status`, reconcile the accepted bubble once, and present execution failure separately from never-sent rejection. No automatic provider replay is authorized. This is the exact downstream attempt API for 02C/03: 02A's `chatSubmissionStore` owns `begin/accept/reject/unknown` keyed by `{workspaceId,threadId,requestId}`, while `thread:action` status supplies authoritative receipt outcome/turnId/content. SPEC-03 must use that API, not install mount-local pending refs.
