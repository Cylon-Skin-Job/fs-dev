> # Custom Theme CSS
>
> ## Use the Theme Picker
>
> The Theme Picker changes the workspace palette and previews changes immediately. It saves the current user theme through the server; the server stores the theme entry in `ai/<machine>/System/styles/themes.json` and generates `themes.css`. The picker offers Light, Custom and Dark modes; switching to Light or Dark snaps the stored luminance into that mode's range. The current picker groups controls by Workspace, Thread, Navigation, Chat and Content. For the generated token and file ownership contract, follow [Themes and State](../../005-Enforcement/002-Themes_And_State/PAGE.md).
>
> ## Hand-authored CSS today
>
> Shared workspace styles live under `ai/<machine>/System/styles/`. The client loads a fixed list of files; simply adding `custom-noir.css` to this directory does not apply it. If a workspace-wide customization is authorized, edit an already loaded authored shared layer with a saved preimage and use existing CSS variables for palette changes. Do not hand-edit generated `themes.css`: activating or saving a theme can replace it. For a single view, current code can load that view capsule's optional `styles/themes.css` as a scoped override; follow the current path and rules in Themes and State. A user-specific editable view instance outside `System` is approved direction, not the current file location.
>
> A short example can show `:root { --bg-primary: #0a0a0a; --document-bg: #1a1a1a; --content-link: #ffb3ff; }` only after checking those tokens against current consumers. Selector-level styling needs a deliberate stylesheet/code change and the relevant CSS standards. An editable instance cannot grant itself plugin capability or executable behavior; protected plugin changes use the deliberate user-mediated route described in [View Configuration And Agents](../../001-Workspaces_And_Views/022-View_Configuration_And_Agents/PAGE.md).
>
> ## Refresh and limits
>
> The app loads shared CSS when it initializes or changes workspace. Theme Picker changes trigger a targeted refresh of `themes.css`. There is no general dynamic discovery of new CSS files in the current loader. A new shared layer requires a product code change to the fixed list in `useSharedWorkspaceStyles.ts` (and the preload lists if immediate initialization matters); that is development work, not a file-drop step. Back up authored CSS before editing it. Do not move `themes.css` to an archive as a replacement procedure.

Avoid suggesting a particular shared file as an unconditional user-edit surface until coordinator confirms authorization and the desired token's consumer. The global `System/styles` root is retained by the approved model, while editable **view instance** resources move outside `System`; these are different concerns.

### D2 — existing enforcement owner, `#css-loading`

> Current shared files are injected in this fixed order: `variables.css`, `themes.css`, `components.css`, `views.css`, `file-viewer.css`, `capture-viewer.css`, `tints.css`. The connection and workspace payloads preload the same list. For declarations of equal cascade priority and specificity, later style tags win. Arbitrary new files in `System/styles` are not discovered by this fixed list. Per-view `styles/themes.css` is a separate scoped path.
