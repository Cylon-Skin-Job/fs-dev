## 4. Proposed integrated destination prose

### Proposed `W/003-Automation_And_Agents/005-Background_Agents/PAGE.md`

Suggested metadata: `name: Background Agents`; `description: Current trigger loading and actions, worker file conventions, and the proposed autonomous workflow boundary.`; `metadata.source-files` exactly `fusion-studio-server/lib/startup.js`, `fusion-studio-server/lib/triggers/trigger-loader.js`, `fusion-studio-server/lib/triggers/trigger-parser.js`, `fusion-studio-server/lib/triggers/cron-scheduler.js`, `fusion-studio-server/lib/triggers/script-runner.js`, `fusion-studio-server/lib/watcher/filter-loader.js`, `fusion-studio-server/lib/watcher/actions.js`, `fusion-studio-server/lib/tickets/dispatch.js`. These are source-file suggestions; the coordinator must recheck exact code and stamp actual edit time. Do not include `ai/<machine>/Agents/Background Workers/` as `source-files`: it is a folder, not an exact code file. Remove old edge/skill/trigger metadata.

> **Status boundary.** Fusion Studio loads declarative triggers and can run their built-in actions. In the booted server path, those actions do not start an autonomous background worker session. The older ticket dispatch and Kimi wire runner still have code in the repository, but the server does not start their dispatch watcher. A trigger-created ticket therefore does not mean a worker has been launched.
>
> **Worker files.** The active Agents registry maps names such as `wiki-manager`, `code-manager`, and `ops-manager` to folders under `ai/<machine>/Agents/Background Workers/`. These folders contain `settings/PROMPT.md`, worker-level `settings/TRIGGERS.md`, named `workflows/` with `TRIGGERS.md` and `WORKFLOW.md`, and memory notes such as `HISTORY.md`, `LESSONS.md`, `MEMORY.md`, and `SESSION.md`. This is a file convention and editable design surface; the current trigger loader does not execute `WORKFLOW.md` or persist a stepped run by itself.
>
> **Trigger definitions.** After an active workspace starts, the server reads its Agents registry and scans registered agent folders recursively for `TRIGGERS.md`. It also scans active view capsules and `ai/components`. A file can contain multiple paired `---` YAML blocks. `file-change` blocks become project watcher filters with events, match/exclude patterns and conditions. `cron` blocks become minute-checked scheduled ticket creators. `chat`, `ticket`, `agent`, and `system` blocks with an `event` field subscribe to matching legacy bus topics. Registration alone does not prove that a producer emits a particular topic or that an example path still matches current files.
>
> **Trigger actions.** The default is `create-ticket`. The action handler registry also contains `log`, `notify`, `send-message`, `webhook-post`, `show-modal`, and `drop-file`. Their required configuration and callback wiring differ by route: cron always creates a ticket, and the file-change loader does not forward all action-specific fields. `send-message` currently broadcasts a legacy `system_message` WebSocket frame; delivery into an active chat thread is not established. A file-change `create-ticket` action alone can run an optional `script`/`function` first and use its result in the ticket template. Treat this as local automation behavior, not governed publication or plugin permission. See the Universal Event Bus standard and Automation Run Provenance Schema for those boundaries.
>
> **Intended worker model.** A future trigger-started worker could select a workflow, follow its `WORKFLOW.md`, preserve memory and record steps under `runs/`. Ticket edits and `@` mentions could also drive routing. These are design directions, not current automatic worker execution. Existing trigger files and ticket actions are useful separately; verify each configured path and prompt reference before relying on it.

The generic example in the old source should be omitted until a valid match path and action are chosen. The live `wiki-manager/settings/TRIGGERS.md` still contains `open-robin-server/lib/**/*.js`, `ai/<machine>/Wiki/project/**/PAGE.md`, and references `PROMPT_01.md`, `PROMPT_02.md`, `PROMPT_03.md`, `PROMPT_AUDIT.md` absent from that worker folder. An article may show a compact schematic without claiming this deployed example works.
