Status: reconciled 2026-09-19 against approved owner direction and inspected development source. Settled targets below are not claims of complete enforcement. Current observations cover the named owners only; no product tests or runtime checks were rerun for this documentation.

## Settled System ownership

`fusion.db` is System. It owns mutable Fusion configuration and controls as well as durable history: chat sessions/threads, groups, chosen metadata, registrations, permissions, subscriptions, ledger, provenance, versions, snapshots and recovery records. “Families” is ordinary product language for grouping, not a request to rename current identities or invent a schema. Historical purpose does not mean cryptographic immutability or universally append-only storage.

Connected applications and services remain authoritative for live email, calendar, notes and similar content. Fusion views display and act on that content through integrations; System is not a second live application database. Workspace applications may use Markdown, JSON, CSV or separate workspace SQLite files. The filesystem `System/` tree and `fusion.db` are related ownership surfaces, not identical stores: existing file-backed configuration and view state need not all move to SQLite. The [Server And Runtime hub](../../../002-Server_And_Runtime/PAGE.md#system-database-boundary) owns the detailed boundary and current calendar exception.

Plugins use defined system interfaces and approved capabilities. Governed events may be supported through those interfaces; a plugin cannot create arbitrary System tables, use System as its own application database, inherit an ambient database handle or grant itself permissions. Platform-owned migrations are distinct from plugin access. This direction does not establish a general plugin activation or emission interface in current code.

Preserve durable history by default; cleanup must be explicit user-controlled policy. Mutable system settings remain mutable. Current deletion and diagnostic-cleanup code still exists and is described in the [hub's current limitations](../../../002-Server_And_Runtime/PAGE.md#current-preservation-limitations); this target does not certify that those routes have been removed or that all history is retained forever.

## Accepted implementation boundaries

| Area | Accepted scope and inspected owner | Limit of the agreement |
|---|---|---|
| Governed facts | `lib/subscriptions/admission.js` seals host-owned publishers for the two mediated-save facts and two agent-observation facts; `controller.js` dispatches admitted frozen facts. | The trusted built-in model replaces older accepted-reference/lease/causal-proof prerequisites only for this bounded save/subscription implementation. It does not authorize arbitrary plugin executors, general causal graphs or broader canonical file versions. |
| Mediated save | `lib/file-mutations/save-controller.js` reserves the operation, reads and durably prepares the preimage before atomic replacement. Eligible input is exact NUL-free UTF-8 text, at most 10 MiB before and after, in a supported regular file; a missing target has an absent preimage and becomes create. | The guarantee covers `file_save`, not arbitrary external changes or the separate move/rename/delete/create commands. Final symlinks, incompatible bytes, oversized files and unsafe paths are rejected. Required preimage failure prevents mutation; provenance is not universally optional on this path. |
| Tool observations | `lib/agent-provenance/resource-observer.js` and its checkpoint repository provide bounded post-tool observations of eligible workspace files; first or changed bytes/absent states can create sparse checkpoints. | These are observations, not tool interception or causal verdicts, and not canonical `file.version` events. The narrower normalized activity/fingerprint/checkpoint/two-fact ledger contract does not approve general tool/native-reference/output artifacts, diffs, retention or restore. |
| Save context | Client `src/lib/save-action-context.ts` reads live registered view/component context; server `lib/file-mutations/reported-ui-context.js` sanitizes it using server-derived workspace authority. | Context is a historical snapshot on the existing save carrier. Malformed/absent fields degrade without rejecting a valid save. It neither writes history back to view state nor implements the general `ui.action` subsystem. |

Server paths in this table begin at `fusion-studio-server/`; client paths begin at `fusion-studio-client/`. These observations were inspected on 2026-09-19. The current admission publisher awaits reservation verification and dispatch, and the controller may await required acknowledgements. `admitted: true` is not a guarantee of subscriber delivery or persistence. Do not import an older universal “no provenance work is ever awaited” rule into this implementation.

## Facts, context and source operations

Commands enter owning services; facts describe accepted commands or completed/observed work. Use the existing event bus and registered ownership rather than inventing a parallel service. Legacy `emit/on`, including watcher and chat paths, still coexists with governed admission. `lib/ledger/event-ledger.js` currently whitelists `workspace:switched`, `thread:state_changed` and `file:changed`; its fallback `user` actor for file events is a heuristic, not authenticated human evidence. Detailed event/schema articles define their own current scope.

A file save's required recovery protection precedes the mutation. Postwrite fact or projection failure is different: it must be handled without pretending the completed filesystem replacement did not happen. Agent observation follows tool activity; missing native support, invalid or ineligible paths and failed observations can leave no checkpoint. A first observation cannot supply bytes from before an already completed tool action.

UI and actor identities have different jobs. The adopted actor taxonomy is `human`, `assistant`, `trigger`, `scheduler`, `script`, `sync`, `import`, `agent`, `system`, `external`, `unknown`; it is not a claim that every current event uses one common envelope. Tab/component identity belongs to context. Current save origin is a reported local-client transport fact, not proof of an authenticated human click. Unknown attribution stays unknown; neither timing nor accepted endpoint identity establishes causation.

The approved retention grain is domain mutations and their initiating UI action context, plus trigger-run results. Ambient clicks, focus, open-tab, scroll and reorder are not durable provenance; potential reaction value on a future bus telemetry channel does not authorize ledger retention. This is target granularity, not proof that every mutation already emits a governed fact.

## Snapshots and restoration

Historical copies belong to audit and recovery. Save preimages and post-tool observation checkpoints are two bounded mechanisms with different timing and eligibility. Neither makes System the authoritative live source of the application content it describes. A restore requires a separate permitted operation against that source, with coverage, conflicts and provider capabilities defined before implementation. No universal restore, full file history or new snapshot policy is approved by the presence of these rows.

## Open product choices

| Future work | Decision needed before implementation |
|---|---|
| Data lifecycle | Exact retention/deletion tiers and durations, user controls, redaction, export, encryption, and reconciliation with current delete/cleanup behavior. Preservation direction is already settled. |
| Restore and wider versioning | Eligible resource classes, snapshots/diffs, restore UI and conflicts, provider capabilities and canonical version events beyond current save/checkpoint contracts. |
| General plugins | Registration, emission and permission grammar, extension interface and enforcement. No arbitrary System storage or self-grants is already settled. |
| Broader provenance | Canonical chat/tool/native-output branches, causal-edge meaning and proof, automation identity generation/lifecycle, saved audit/query/recommendation contracts and storm thresholds/capacities. Eventual automation facts require a durable run identity and kind; exact generation and subtype rules remain open. |
| Calendar alignment | Replace or migrate the existing live-content SQL projection toward source-authoritative integration. No data deletion, migration or alternative runtime is authorized by documenting the gap. |

Older detailed envelope, accepted-reference, executor-capacity, lease, token, storm-batch and graph proposals are not current APIs or automatically approved future requirements. The bounded save, tool-observation and context agreements settle only their exact subjects. When new work reaches another branch, resolve the material product choice then; do not use a draft to invent runtime permissions or reopen a settled System decision.

## Planning rule

Read this boundary and the source-inspected current behavior first. Apply settled decisions, verify relevant source at build time, distinguish a known implementation gap from a missing choice, and ask the owner only for material missing or conflicting intent. Chat identity and lifecycle remain owned by [Chat System](../../../007-Chat_System/000-Overview_and_References/PAGE.md); a provenance reference does not replace those contracts.
