A **view definition** describes how a kind of content is displayed and handled. An **installed view instance** is a particular workspace's configuration and local resources. Its **content root** is the material it reads or edits, which may be elsewhere in the project folder. A **tab** presents content inside the view. None of these is interchangeable. The [approved direction](../000-Workspaces_And_Views/001-Vision/PAGE.md) makes the definition a protected view plugin and the instance an editable folder referencing it. A plugin can instead define a workspace composition; plugin does not always mean view.

## Current view discovery

Today the server discovers numbered folders under `ai/<machine>/System/Views/`. Each folder's `manifest.md` declares a canonical, unique `metadata.view-id`; its `name` is the display label. The numeric folder prefix controls order, with folder-name sorting as a tie-breaker. The prefix and label are not the durable ID. `content.json`, styles and state are within the instance folder, often called a **capsule** in code. The target moves editable instances outside System, while protected plugins stay there; the exact destination is still open. This current folder convention is not the future plugin schema.

**WV-G03 — repeatable plugin-defined instances:** the current discovery and bundled Add View route require unique view IDs and reject a second installed copy of the same template. `baseViewId` in the current registry projection equals the instance ID; it does not yet give multiple independent instances of one plugin. `ContentArea.tsx` dispatches built-in React components by fixed IDs, with separate custom/browser iframe cases and an unknown-view placeholder. The remaining capability is a plugin-to-instance binding and display dispatch that allows distinct instance identities while retaining the protected plugin's permissions. The platform view registry and renderer own that work. The identity/schema and binding rules remain a product gate (WV-O04); instance update/remove behavior is also open (WV-O02). A template folder alone does not establish this capability.

## Approved presentation boundary

A protected view plugin supplies content behavior and may contribute reusable presentation through the platform host contract. Its template is copied into a separate editable instance; configuring or composing registered components there does not create executable authority. Components render on the client from explicit data/actions. The platform shell retains tab, drawer and popup/window identity, focus and lifecycle; the canonical file-type registry and file surface retain presentation/editing, with save/history owned by platform services. A collection may open that file surface in its current tab with a return route or another tab while retaining selection/filter/navigation state. This is approved direction, not a claim that fixed current dispatch implements a general plugin loader or a second tab/save store. See [Composable Presentation](../../011-Platform_And_Plugins/003-Composable_Presentation/PAGE.md) and [Tabs, Drawers And Files](../../011-Platform_And_Plugins/004-Tabs_Drawers_And_Files/PAGE.md).

## Content is a separate binding

The server reads a view's `content.json` and resolves a declared root separately from the capsule. Current supported declarations include workspace-relative, machine-relative, view-relative, project-root, selected-folder, absolute, SQLite and none; relative paths are checked against their allowed roots. The default `wiki-viewer` root is `ai/<machine>/Wiki`, `capture-viewer` uses `Captures`, and `file-viewer` uses the project root or session root. Changing a content root is configuration within the existing view implementation, not installation of a new view or a new grant of authority. The target requires plugin binding and content-root validation before treating an editable instance as safe; this page does not claim that future enforcement is already complete.
