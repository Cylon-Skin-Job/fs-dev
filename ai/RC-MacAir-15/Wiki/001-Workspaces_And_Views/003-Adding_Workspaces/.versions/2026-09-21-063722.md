The ribbon offers **Add Project** for an existing folder, **Create New** for a new project, and **Add to ribbon** for a registered but hidden workspace. These are different actions. A project folder need not be a Git repository. [Workspace Paradigm](../001-Workspace_Paradigm/PAGE.md) explains the identity boundary.

## Add Project: register an existing folder

The Add Project modal warns that the folder must already contain `/ai`, then opens a folder picker. The client sends `workspace:add_requested` with `repoPath`; the WebSocket handler forwards the request to the server controller. The controller canonicalizes the existing path, rejects a duplicate registration or missing `ai`, creates an ID and registry row, prepares the view registry, and then bootstraps minimum machine-scoped directories when readiness allows. It broadcasts the resulting registration; readiness failure is reported as unavailable. Bootstrap is limited to `System/Views`, `System/config`, `System/state`, `System/styles` and `Data` beneath `ai/<machine>/`. It does not populate the five default views or turn an ordinary no-`ai` folder into a workspace. The latter is the open WV-G01 / WV-O05 decision, not a missing step the agent should improvise. The current missing-`ai` alert still refers to Create New as a future flow, although the Create New menu and handler exist; that alert wording is stale.

## Create New: scaffold from bundled templates

The Create New modal fetches a manifest and displays the included views. Its form accepts a project path and optional display name; the request sends those fields, not the displayed view IDs. The controller requires an absolute target with an existing parent and either a missing or empty target, then calls `create-service.js`. The **current `new` profile** selects five views: Capture (`capture-viewer`), Files (`file-viewer`), Wiki (`wiki-viewer`), Issues (`issues-viewer`), and Agents (`agents-viewer`). Calling Capture `doc-viewer` is stale for this profile. The service copies selected bundled templates from `System_Manager/ai-template/templates/view-templates/` to numbered `ai/<machine>/System/Views/` folders, copies the needed data roots, and initializes workspace-local data. It then registers and activates the workspace. The server's scaffold function accepts view IDs internally, but the current Create New UI/request does not expose an editable composition selector.

## Registration, ribbon and readiness

The SQLite `workspaces` registry keeps the workspace ID, label, canonical path, type, order, ribbon visibility and ribbon order. Hide from ribbon updates visibility while preserving registration; adding it back restores membership. A full remove request deletes registration and associated workspace-owned database rows, not the project folder. At startup, readiness and path/structure checks identify unavailable registered workspaces without deleting their rows; the last available active workspace is restored or another available row selected. On switch, the server publishes the new binding and sends a view registry/content-root projection for the client to render. A registered folder can therefore be visible in the registry while its view registry is unavailable.

The [intended composition flow](../021-Workspace_Compositions/PAGE.md) instead uses installed workspace and view plugins and server-owned provisioning. The current template copy is real, but does not prove that plugin installation, dependency policy or instance relocation is shipped. These routes were inspected in source; no app runtime behavior was certified by this documentation pass.
