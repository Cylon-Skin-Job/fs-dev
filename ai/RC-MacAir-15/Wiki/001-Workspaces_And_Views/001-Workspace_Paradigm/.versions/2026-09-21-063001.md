A **project folder** is an ordinary folder on disk. It need not be a Git repository. A **workspace** is Fusion Studio's registered binding to that folder, plus the configuration and presentation used while working there. The workspace ID, display label, path, ribbon position and visibility are separate registry properties; renaming a label or hiding a ribbon item does not create or destroy the underlying project folder. Reader, router and executor describe possible responsibilities for work, not three different workspace identities.

## What is registered today

The server's workspace registry stores an ID and canonical project path in SQLite. The controller validates an existing folder before Add Project, checks for a duplicate registered path, requires its `ai` directory, and inserts a workspace row. The current UI warns about this prerequisite. **WV-G01 — attaching an ordinary folder:** automatic creation of `ai` on attach has not been approved; Add Project currently rejects a folder without it. The remaining capability, if chosen, is a defined initialization path owned by the workspace controller and bootstrap service. The owner must first decide [whether ordinary folders should be initialized automatically](../000-Workspaces_And_Views/002-Decisions/PAGE.md#open-product-choices) (WV-O05). Existing-folder bootstrap creates minimum machine-scoped `System` and `Data` directories; it does not copy the five default views.

Current machine-specific configuration, view folders, wiki and other local content live under `ai/<machine>/`. `ai-paths.js` resolves that machine name; changing machines can select a different subtree within the same project folder. This is an observed path convention, not a decision that every future instance resource must remain machine-specific. The exact destination and portability of editable view instances remain open (WV-O01).

A workspace can have multiple view instances. Each view has its own identity, display label, ordering and content binding; a tab within a view is a content presentation, not another workspace or installed view. See [View Architecture](../002-View_Architecture/PAGE.md). Workspace registration alone does not mean a view is installed, visible, or ready.

## Availability and switching

At startup, the controller checks registered paths and structure and restores the last available active workspace, falling back to another available row when needed. Unavailable rows remain registered. Switching updates the active binding and sends workspace and view information to clients; it does not provision a new composition. Removing a workspace registration is different from removing it from the ribbon. [Adding Workspaces](../003-Adding_Workspaces/PAGE.md) follows those paths.

[Workspace Compositions](../021-Workspace_Compositions/PAGE.md) explains the approved plugin model and its current limit. [Chat System](../../007-Chat_System/000-Overview_and_References/PAGE.md) remains the authority for thread and session identity within this shell; workspace identity does not redefine it.
