Use this section for backend ownership, runtime state, persistence, WebSockets, filesystem resolution, and service behavior.

## System database boundary

Status: this ownership boundary is approved direction; the current database/calendar/delete observations below were source inspected on 2026-09-19 in the development checkout. Other runtime sections retain their existing scope. This is not a recent runtime pass or an app-wide storage audit; installed Alpha was not inspected.

`fusion.db` is System: it owns mutable Fusion configuration and control records alongside durable chat and history. That domain includes sessions/threads, groups, chosen metadata, registrations, permissions, subscriptions, ledger/provenance, versions, snapshots and recovery records. `lib/db.js` selects `fusion-studio-server/data/fusion.db` in development or `${FUSION_APP_USER_DATA}/server-data/fusion.db` when configured, and initializes the shared Knex database and migrations.

Connected apps/services remain authoritative for live email, calendar, notes and similar content. Fusion views display and act through integrations; System must not become a second live application-content database. Workspace apps may use Markdown, JSON, CSV or a separate workspace SQLite database as their own content. Such a file is not `fusion.db`. The machine-scoped filesystem `System/` tree holds configuration/view state as well: System ownership does not mandate moving every existing setting or state file into SQL.

Plugins use defined system interfaces and approved capabilities. They may generate governed system events through an approved interface, but cannot create arbitrary System tables, use System for application storage, receive ambient database authority or grant themselves permission. Platform-owned schema evolution stays behind platform migrations and owning services. This target is not evidence that a general plugin interface or complete filesystem protection is already enforced.

Historical snapshots are audit/recovery copies, not an editable replacement for the authoritative source. Restoring a copy is a separate permitted operation against that source. Preserve durable history by default, with explicit user-controlled cleanup policy; mutable control records still change normally. See [Events And Ledger Decisions](../010-Events_And_Ledger/000-Events_And_Ledger/002-Decisions/PAGE.md) for accepted snapshot limits and remaining product choices.

## Current calendar storage gap

Current source conflicts with the source-authoritative target: `lib/calendar/db-writer.js` uses the same `getDb()` singleton to upsert `calendar_sources` and `calendar_events`. Migration `022_calendar_sync.js` stores calendar titles/colors and live event content including title, dates and description. This is an existing implementation gap, not permission to add similar email/notes tables to System. Removal, migration and replacement access need later product work; no change to user data follows from this documentation.

The source path is conditional. `lib/startup.js` initializes the DB and invokes `calendar.start()` as a startup effect. `lib/calendar/index.js` checks `background-services/config.js` opt-ins: defaults are disabled, with configuration or environment overrides. Apple additionally requires the local Calendar database; `watch/calendar-watcher.js` triggers `calendar/apple/sync.js`, which reads and converts a bounded date window and then upserts. Google `calendar/google/poller.js` initiates and periodically runs `google/sync.js`; `google/client.js` requires configured bridge URL/key, and missing configuration/results skips writes. Source-present tables and writers do not prove sync is enabled or any user's database contains rows.

`server.js` mounts `lib/http/calendar-routes.js` at `/api/calendar`. GET `/calendars` reads `calendar_sources`; GET `/events` reads the overlapping date range from `calendar_events`, optionally filtered by source. Client `src/state/calendarStore.ts` exposes `fetchCalendars` and `fetchEvents` to map those responses into Zustand. `lib/ws/calendar-broadcaster.js` forwards `calendar:sync_complete`; client `src/lib/ws/calendar-handlers.ts`, registered by `ws-client.ts`, calls `fetchEvents` on the visible range.

The actual mounted `src/components/calendar/CalendarViewer.tsx` initially calls `loadDemoData`, not those HTTP readers. It renders the store's calendars/events through `CalendarMonthView`; the sync handler can later fetch events even in demo mode. Current store create/update/delete methods only warn that write-back is deferred. Therefore neither the mounted calendar nor these helper definitions prove a functioning live round-trip integration. Client paths above start at `fusion-studio-client/`; server paths start at `fusion-studio-server/`.

## Current preservation limitations

Preservation is a target, not an assertion that all current System rows are immutable. `lib/thread/ThreadManager.js#deleteThread` calls the owning index deletion, whose `threads` deletion cascades to exchanges. The agent-provenance migration clears an activity's nullable exchange binding/clocks when an exchange is deleted; checkpoint storage is separate. This is not a general restore guarantee. [Chat lifecycle](../007-Chat_System/006-Runtime_Model/PAGE.md) owns the detailed group/session behavior.

`lib/thread/harness-diagnostic-service.js` also implements bounded cleanup for its dedicated diagnostic table: expiry at 30 days and caps of 500 rows per workspace and 5,000 total, applied during insertion and startup cleanup. These inspected limits are current behavior, not newly approved universal retention policy. Exact lifecycle policy and reconciliation with preservation remain future decisions; this bounded check does not enumerate every application's deletion path.

## Current Workspace Lifecycle Runtime

- The workspace registry lives in the server SQLite database. `registry-service.js` is pure data access; `workspace-controller.js` owns lifecycle decisions and emits events.
- `workspace-request-handlers.js` receives WebSocket requests and emits event-bus requests. `workspace-broadcaster.js` turns controller events back into WebSocket messages.
- Add Project requires an existing `/ai` folder and calls `bootstrap-service.js` to create only the minimum machine-scoped V2 folders.
- Create New calls `create-service.js`, which copies from `System_Manager/ai-template`, creates selected numbered view capsules, creates the workspace mirror database, registers the workspace, and switches to it.
- Launch availability checks warn and emit status for missing or invalid registered workspaces, but do not delete registry rows.

For the full user and code path, see [Workspaces And Views > Adding Workspaces](../001-Workspaces_And_Views/003-Adding_Workspaces/PAGE.md).

## Current View Path Runtime

- `fusion-studio-server/lib/views/index.js` is the V2 view resolver. It discovers `ai/<machine>/System/Views/NNN-view-id/` capsules, loads `manifest.md`, `content.json`, `styles/icon.md`, and `styles/layout.json`, and resolves declared content roots.
- `fusion-studio-server/lib/views/panel-paths.js` maps view panels only through the canonical `ai/<machine>/System/Views/` registry. The unrelated legacy System workspace/styles readers remain limited to their non-view compatibility surfaces.
- `fusion-studio-server/lib/file-explorer.js` serves WebSocket tree/content requests and virtual V2 metadata aliases such as `__workspace__/views.json` and `__panels__/<view-id>/...`.
- `fusion-studio-server/lib/http/panel-file-route.js` serves files from the same resolved panel path as the WebSocket file explorer.
- `doc-viewer` resolves to `ai/${machine}/Captures`; normal root listings hide `999-Archive`, while Archive mode lists that folder directly.
- `office-viewer` resolves to `ai/${machine}/Office`; normal root listings hide `999-Archive`, while Archive mode lists that folder directly.
- `wiki-viewer` resolves through `content.json`, defaulting to `ai/${machine}/Wiki`.

Viewer search is client-side over these resolved panel paths. The server supplies `file_tree_request` and `file_content_request`; view adapters decide search scope and exclusions. See [Viewer Search](../001-Workspaces_And_Views/012-Viewer_Search/PAGE.md).

## Current View State Runtime

View-local state is resolved by `fusion-studio-server/lib/view-state/resolver.js` and written by `writer.js`. The client sends `state:get` and `state:set` messages. The server deep-merges workspace defaults with the per-view state file under the numbered view capsule.

The following view-local branches are intentionally persisted in `state/state.json`:

- Capture mode, selected path, grid scroll, and document scroll.
- Office document Recent drawer state.
- Shared `activity` for recents, wiki navigation, and File Explorer tabs.
- Shared `collections` for starred files and Office pinned folders.

The server does not own viewer recents through the old Recent Docs SQLite path. Recents are view-local state now. File rename/archive/restore/delete flows call shared path-reference cleanup so activity and collections stay aligned with filesystem changes.
