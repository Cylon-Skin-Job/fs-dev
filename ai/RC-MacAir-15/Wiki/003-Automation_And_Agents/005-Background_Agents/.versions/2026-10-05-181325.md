## Status boundary

Fusion Studio loads declarative triggers and can run built-in actions. In the booted server path, these actions do not start an autonomous background worker session. The older ticket dispatcher and runner have code in the repository, but normal startup does not mount the dispatch watcher. A trigger-created ticket therefore does not mean a worker launched. [Ticketing](../002-Ticketing/PAGE.md) owns the board and creation gap; [Run Auditing](../004-Run_Auditing/PAGE.md) owns legacy run records.

## Worker files

The current Agents registry maps names such as `wiki-manager`, `code-manager` and `ops-manager` to folders under `ai/<machine>/Agents/Background Workers/`. These folders contain `settings/PROMPT.md`, worker-level `settings/TRIGGERS.md`, named workflows with `TRIGGERS.md` and `WORKFLOW.md`, and memory notes including `HISTORY.md`, `LESSONS.md`, `MEMORY.md` and `SESSION.md`. This is a file convention and editable design surface. The trigger loader does not execute `WORKFLOW.md` or persist a stepped run by itself.

## Trigger definitions and actions

After an active workspace starts, the server reads its Agents registry and scans registered agent folders recursively for `TRIGGERS.md`. It also scans active view capsules and `ai/components`. A file may contain multiple paired YAML frontmatter blocks. `file-change` blocks remain in trigger definitions but have no active watcher input and do not fire automatically. `cron` blocks are checked by minute and attempt ticket creation. A configured cron condition is evaluated with an empty variable context; if false, a configured retry duration schedules one recheck, which creates a ticket only if the condition then passes. This does not establish that example conditions requiring chat or ticket context work. `chat`, `ticket`, `agent` and `system` blocks with an `event` subscribe to matching legacy bus topics and continue to register through the event path. Registration does not prove that a producer emits a topic or that an example path matches current files.

Templates substitute `{{key}}` and one-level `{{object.key}}` placeholders from the variables supplied by that trigger route; unavailable variables become empty text. The default action is `create-ticket`. Other registered handlers include `log`, `notify`, `send-message`, `webhook-post`, `show-modal` and `drop-file`. `notify` broadcasts a `file_changed` frame when its callback is wired; `show-modal` broadcasts a configured modal only when its definition and callback exist; `drop-file` writes expanded content under the project root after lexical containment and protected-view checks. These are handler capabilities, not guarantees that every trigger route forwards the necessary fields. Configuration and callback wiring differ by route: cron always creates a ticket, and the file-change loader omits several action-specific fields. Its optional script wrapper applies to file-change ticket creation, not every action. `send-message` broadcasts a legacy `system_message` WebSocket frame; delivery into an active chat session is not established. These paths are legacy local automation, not governed event publication or plugin permission. See [Universal Event Bus Standards](../../005-Enforcement/001-Code_Standards/005-Universal_Event_Bus/PAGE.md) and [Automation Run Provenance](../../010-Events_And_Ledger/003-Provenance_Model/006-Automation_Run_Provenance_Schema/PAGE.md).

## Intended worker model

A future trigger-started worker could select a workflow, follow `WORKFLOW.md`, preserve memory and record steps under `runs/`. Ticket changes or mentions could also drive routing. These are design directions, not current automatic worker execution. Existing trigger definitions need their match paths and prompt references verified before reliance; the bundled wiki-manager examples still mention old product paths and missing prompt files.
