## Current understanding

The owner favors building plugin infrastructure sooner and used ai/plug-ins as a possible home. The newer plugin vision specifies a flat protected System/plugins/<plugin-id>/ tree and editable view instances outside System. Older fs-dev summaries still use category directories. These sources need one explicit reconciliation before implementation.

In the 2026-09-29 owner discussion, a custom view was framed as an app composed of protected plugin functions and display modules. The view can request file content from Fusion, invoke a named app function for a short app-owned database write, and receive a result while authorized subscribers receive the admitted outcome fact. The owner also wants declared cross-plugin capability use, approved System audit/log queries, and meaningful UI-action subscriptions. These depend on registration and grants; raw DOM interaction, arbitrary UEB emission and direct `fusion.db` writes are not implied. See [D-003 and D-004](DECISIONS.md) and the [current UI-action boundary](../../../Wiki/010-Events_And_Ledger/011-UI_Action_Provenance_Module/PAGE.md).

The owner described existing workspace screenshot transitions and focus warming, with thread/view shutdown behavior already considered. Plugin functions should attach to that lifecycle; a view leaving the screen does not by itself terminate server-owned background work. View-surface session binding may need a later adjustment. The existing [workspace ribbon contract](../../../Issues/inbox/RCC-0076.md) preserves server work while a workspace is hidden; this discussion does not certify a general plugin runtime today.

The owner clarified on 2026-09-29 that even bundled/native apps must not put live app domain data in `fusion.db`; [D-006](DECISIONS.md) records that boundary. SoloBooks can own a separate database. The owner imagines using Fusion's audit/recovery history to reconstruct that database, or at least the variables sent to it, but has not chosen whether input strings are retained. That choice matters: metadata or hashes can prove a call happened but cannot recreate omitted values; full inputs and piecewise edits can support replay only if initial state, order, schema/logic versions, and every relevant mutation are available. Storing full inputs in Fusion's audit is also a secondary copy of app data even if there are no app tables. [I-008](ISSUES.md) keeps recovery and payload retention distinct from the settled storage boundary. Current [file-versioning coverage](../../../Wiki/010-Events_And_Ledger/006-File_Versioning/PAGE.md) is bounded; it does not promise recovery of every deleted file.

**Apple-native freshness question (2026-10-03):** The owner plans Apple-first Mail and Calendar integration, with Mail/Calendar retaining their live data rather than Fusion building a second domain store. Full read/write/assistant tooling is later scope, but monitoring must be timely and avoid the reported Chokidar handle pressure. The approximately 30-minute scan in D-015 is only a repository-file fallback. For Calendar, Apple's EventKit posts an `EKEventStoreChanged` signal to an authorized running client and tells it to refetch; a small native helper or bridge is a candidate for Fusion. For Mail, Apple's supported arrival hooks are a MailKit message-action extension during download and user-configured Mail rule scripts. Neither cited hook promises all read, move, delete or cross-device state changes, so a bounded Mail automation query, with short foreground cadence, deduplication, one in-flight operation and backoff, is a candidate reconciliation fallback. This is a planning inference, not a chosen implementation or measured latency. Mail itself must first obtain messages from its account, and automation requires user permission. Prefer a per-connector change signal that makes the UI refetch needed content on demand, rather than copying native app rows into `fusion.db` or writing one durable ledger row per poll. Current Fusion Apple Calendar code uses a directory watcher, private SQLite reader and `fusion.db` writer; the planned boundary needs explicit reconciliation. [I-021](ISSUES.md) holds latency, coverage, lifecycle and resource decisions; [REF-020](REFERENCES.md) records the bounded evidence. The 16,000-open-handle cause and chat failure remain the other session's diagnosis, not a finding of this review.

## Open discussion

Reconcile the exact installed package root and package/instance boundaries; select a minimum real proving plugin; define only the contract and grants that proof needs. See [ISSUES](ISSUES.md) for decisions and source gaps that could change the result.

**Proposed call shape for planning:** every renderer-to-server function or query call is asynchronous at the transport boundary. No separate catalog of “normal” versus “async” functions is needed. A short command can await its owning transaction and return a typed result in the same request. A long-running command can return an accepted run ID and report progress/completion through admitted facts and subscribers. Every call has an outcome and a pre-execution grant/rate check under [D-005](DECISIONS.md). The exact declaration grammar, timeout/budget, cancellation, idempotency and event schemas are open; [I-004](ISSUES.md) tracks the contract. A plugin's own view may call its function directly; cross-view UI-action subscriptions require a named host-published action and an approved grant, tracked by [I-005](ISSUES.md).

**Recorded history and new plugin listener direction (2026-10-03):** The earlier owner discussion is preserved as scoped decisions [D-003 through D-005](DECISIONS.md), this proposed call shape, [I-004 through I-007](ISSUES.md), and [REF-005](REFERENCES.md); it is not a complete verbatim history checkpoint. A view or agent invokes a named authorized server function, receives its typed outcome asynchronously, and an admitted result fact may separately reach UEB subscribers. The owner now adds a second ingress: a protected Mail/Calendar plugin owns the native listener or scheduled source query, while System supplies an interval capability, registration/grants, lifecycle and governed fact admission. The listener reports a verified source change; System stamps trusted provenance and admits a typed UEB fact; authorized views, other plugins and triggers subscribe. A raw EventKit signal or poll tick is a cue to inspect source state, not automatically an item-change fact. A subscriber seeking to change data invokes its own authorized named command. The native listener must continue with the plugin's server-side enabled lifecycle even when its view is hidden, while interval work remains bounded and cancellable. Bus publication, UI refresh and durable ledger retention are separate effects; the exact ordering and which facts persist remain open in [I-022](ISSUES.md). This follows the [current governed UEB command/fact boundary](../../../Wiki/010-Events_And_Ledger/001-Universal_Event_Bus/PAGE.md) without claiming general plugin publishers/subscribers are implemented today.

**Open read-observability question:** a typed, authorized read of `fusion.db` is still an asynchronous server query to the caller, but the owner asked whether every such read should publish a separate UEB fact. The earlier [plugin vision](</Users/rccurtrightjr./projects/plug-ins/ai/RC-MacAir-15/Captures/001-Plugin_System/VISION.md>) says reads stay liberal and light and mutation records are the ledger's currency. A blanket durable read event could create volume and disclose query context. [I-006](ISSUES.md) keeps the policy choice open; scoped query responses and rate controls do not depend on resolving it.

**Latency direction from the same discussion:** the owner wants tool calls and native Mail/Calendar pass-through to stay responsive. A callable must await the operation whose result it claims, including grant checks, the owning transaction and required prewrite protection. Optional subscribers, projection and telemetry should be kept out of that critical path where the governing contract permits; a slow operation may return a run ID and stream progress. The current governed UEB can await required acknowledgments and mediated file save requires a prepared preimage, so “never await UEB” would contradict accepted behavior. The archived [connector vision](</Users/rccurtrightjr./projects/plug-ins/ai/RC-MacAir-15/Captures/001-Plugin_System/VISION.md>) describes live native reads served from RAM without silent persistence. [I-007](ISSUES.md) tracks bounded latency and connector handoff; plugin packaging alone does not establish responsiveness.

**Historical repo-local snapshot proposal (2026-09-29; ownership/storage direction now clarified by D-015, exact path/migration still open):** The owner proposed a snapshot database inside each repo's AI/System/Data area, with file-reference and ID links to UI and agent records. The aim is recoverable file versions plus reasonable inference about why a change appeared, without labeling provenance as conclusive truth. The current workspace layout has `ai/<machine>/Data/`, and no `ai/<machine>/System/Data/` in the inspected repo, so exact path, machine scope and whether this replaces existing System snapshot tables remain open in [I-016](ISSUES.md). Under the proposed capture rule, a manual edit in a canonical file tab creates a version; opening a file in a tab also reads current bytes, compares them with the last stored hash and creates a deduplicated observation only if changed. A tab-open difference establishes that the file changed since the last observation, not who changed it or how many intermediate states existed. The snapshot reason should remain distinguishable (`tab_save` versus `tab_open_observation`) and carry file identity, hash, observation time and optional initiating event/tool link. Existing mediated save already requires a durable preimage before replacement; a repository-local move must preserve that protection or explicitly reconcile the accepted save contract with its owner. Current agent observations also create sparse deduplicated eligible UTF-8 checkpoints in `fusion.db`; moving or narrowing them is separate scope, not an automatic consequence of this proposal. **Historical content-light UI and app-database facts (2026-09-29; tab-only/watcher timing alternatives superseded by D-015):** A meaningful form save or field edit that mutates JSON would record the UI operation, field/resource reference and result without the entered value. The watcher-inclusive choice could capture the stabilized JSON change sooner if it is eligible and observed. For a self-contained invoice app, a UEB fact could identify changed table/row and owning command without copying values into Fusion; invoice row history/versioning stays in its own database and is outside the file snapshot database. Agent tool activity can link thread/turn/tool-call and candidate file/resource references, while raw tool syntax or query text may be retained with its Chat exchange. Parsing that syntax is only an inference: current shell extraction is bounded, incomplete for dynamic commands and does not parse arbitrary SQL/app effects, and another writer may act before observation. An app-owned command receipt with a row ID is stronger than syntactic inference when the app can provide one. [I-017](ISSUES.md) routes UI/UEB schema and cross-domain linkage to their owners; this folder only shapes what a plugin function declares and returns. **Historical selectable watcher or tab-only recording (2026-09-29; capture alternatives superseded by D-015):** The owner chose Chokidar as an option: a repo can retain eligible changes observed by the filesystem watcher, or limit durable file versions to Fusion-recorded edits through the canonical file tab, with a record-selection config beside the proposed repo-local snapshot DB. [D-013](DECISIONS.md) records that choice. The current server already depends on Chokidar 5 and centralizes watchers in `lib/watch/core.js`; `workspace-watcher.js` applies excludes, a two-second delete/create rename heuristic and emits legacy `file:changed`. The core uses `ignoreInitial` and `awaitWriteFinish` and shares one watcher per path; its first subscriber's options win. A snapshot consumer needs its own scope/filter and must exclude its DB/config from self-observation. Chokidar events are observations, may coalesce writes, and do not establish every intermediate mutation or actor. Broad mode should read eligible stabilized content, dedupe by content hash, and label the record as watcher-observed. Tab-only mode can keep watcher delivery for UI freshness while declining optional durable watcher snapshots. The existing ledger currently records some legacy `file:changed` events, so a user choice about “internal DB” requires a deliberate ledger-retention boundary, not only changing the new snapshot writer. Required mediated-save preimages and core System state cannot be silently disabled by a folder config; [I-019](ISSUES.md) tracks exact categories and migration. See [REF-016](REFERENCES.md).
