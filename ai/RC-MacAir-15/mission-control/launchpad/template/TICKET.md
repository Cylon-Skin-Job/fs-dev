# TICKET — Intake brief template

> Inert starter: adapt to one assigned body of work. This brief describes the assignment and links its authority and evidence; creating it does not authorize execution or certify completion.

A ticket is a working conversation backed by a durable folder. Keep its source-native ID if one exists; do not invent a second tracking identity. The responsible session may change while this folder and its audit history persist. Use the shared [ticket workflow](../../ticket-workflow.md), adapting the link if the folder depth changes.

## Problem or Objective

What prompted the work, for whom, and what should improve? State the reported problem or desired outcome before choosing a solution. Link the original request and distinguish owner statements from agent summaries. After shaping, INTENT and DECISIONS own accepted direction; summarize and link them here.

## Evidence and Reproduction

What was observed, where, and against which revision or environment? For a bug, record expected versus actual behavior and the smallest known reproduction. Label reports that have not been reproduced. Link sources and limitations in REFERENCES; avoid copying entire logs into the intake brief.

## Scope and Exclusions

What is included, explicitly excluded, or still unknown? Link affected code, wiki, consumers and other work in CHANGE_SURFACE when established. Name dependencies or concurrent work that could change the assignment. Unexamined surfaces are not implicitly out of scope.

## Success Conditions

What observable outcome would establish success? Include a candidate smoke scenario and nearby regression concerns when meaningful. Link the eventual verification report; proposed checks are not passing evidence. Keep review, implementation, integration and owner acceptance distinct.

## Unresolved Intent

Which assumptions or decisions could change the result? Link consequential questions in ISSUES, with affected scope, decision owner and next action. Keep tentative ideas in CAPTURE or PROPOSALS. Intake may be incomplete; do not fill gaps with invented intent.

## Authority and Assignment

Link the actual owner instruction or delegated authority. Identify the responsible session when verified, manager, exact memory folder, separate implementation checkout when assigned, allowed operations, owned write areas, exclusions and stopping conditions. Distinguish permission to investigate, propose, implement, commit, open a PR and merge. Full Access and a filename grant none of these by themselves.

## Progress and Return Point

Maintain a compact current summary: phase, active assignment and evidence links, last check, last substantive progress, blocker or intentional wait, next action and responsible owner. Record the verified session link the owner can return to; leave unavailable identity explicit. Use the workflow's return classifications. Mission Control's registry points here rather than becoming a second detailed ledger.

## Work and Review Record

Link each investigation, proposal, review, repair, verification and approval in order, including its input revision, report location and disposition. Use separate assignment directories for evidence; preserve earlier reports. Record superseded scope and why it changed. At closure, link the final candidate, checks, unresolved limitations, integration state and acceptance source; closure for duplication or supersession is different from delivery.
