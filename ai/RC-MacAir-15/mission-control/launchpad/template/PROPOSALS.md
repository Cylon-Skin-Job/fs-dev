# PROPOSALS — Candidate approaches template

> Inert starter: adapt to the assigned subject. Possible responses to intent and issues. A proposal's approval status must link to an explicit owner decision; this file does not create competing approval authority. No proposals exist in this template.

Use stable subject categories and neutral `P-` IDs. Bold-label bullet fields: **Category**, **Status**, **Source**, **Addresses**, **Proposal**, **Alternatives and tradeoffs**, **Dependencies**, **Decision**, and **Related**. Status is proposed, approved, rejected, deferred, or superseded. Use “none yet” for an undecided proposal; approved records identify the actual decision and its approved scope.

Keep the owner's desired outcome separate from the mechanism proposed to achieve it. Explain which issue/outcome the proposal addresses and what would change. If only part is approved, split or clearly scope the record so remaining ideas stay proposed. Keep rejected and superseded alternatives discoverable when they explain the current direction.

Before treating a proposal as awaiting an answer, check its linked decision and relevant later owner statements using the [conversation evidence contract](../../conversation-evidence.md). Source identifies the original suggestion; Decision identifies the actual owner disposition and scope. If approval is implied only by an assistant interpretation, leave it proposed and record the uncertainty. No separate APPROVALS.md is introduced by this convention.

## Candidate Approaches

What options could achieve the desired outcomes, and what are their tradeoffs? Which assumptions need bounded investigation before the owner can choose?

## Validation and Follow-up

What research, demonstration or later activity might resolve a concrete uncertainty? Listing it is not a dispatch or implementation approval; use the investigation contract for authorized research assignments.
