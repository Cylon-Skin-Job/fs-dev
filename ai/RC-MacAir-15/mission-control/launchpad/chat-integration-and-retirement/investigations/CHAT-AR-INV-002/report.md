## Answer and ranked hypotheses

1. **Most relevant: the real OpenCode child fails at or just after per-turn launch.** The server ACKs after the receipt and group activity transaction, then separately claims dispatch and consumes `wire._sendMessage` (`runtime-prompt-admission.js:170-215`, `runtime-dispatch.js:129-182`). All four I-007 receipts are `accepted / claimed / provider_failed`, which means the accepted iterator's catch ran. OpenCode readiness is an in-memory deferred proxy (`harness/compat.js:144-167,282-310,320-356`); its `pid` is null at readiness, and the actual `opencode run` child starts in `OpenCodeHarness.sendMessage` (`harness/opencode/index.js:152-200`). Thus a successful session bind or `wire_ready` does **not** prove the CLI child launched or bound an OpenCode session. The absence of new OpenCode records at the incident times is compatible with a spawn failure, immediate CLI exit, bad working directory/arguments/environment, or failure before usable output. It does not distinguish them. The live receipts' `created_at` to final `updated_at` intervals were 15–19 ms for the four recent failures, consistent with a fast path, but no intermediate dispatch timestamp is stored, so this is not a measured child lifetime.
2. **Possible: an adapter failure after launch but before durable provider-session binding.** The OpenCode adapter buffers a provider session ID from parsed events and writes it back only near iterator completion (`harness/opencode/index.js:209-224,278-312`). A spawn error is rethrown raw, a nonzero or incomplete process exit becomes a `HarnessRuntimeError`, and a clean run with no OpenCode session ID throws a plain generic error. A session-ID persistence failure can also throw at the same point. The four recent failures span one thread that currently has a stored OpenCode session ID and one that has none (read-only metadata query); a stale saved ID alone cannot explain the whole cluster. No native event or exact exception was available to select one branch.
3. **Lower-confidence alternate: transient harness metadata lookup silently changes provider.** `harness/compat.js:73-91` catches any DB error in `getHarnessInfoForThread` and returns `harnessId: 'kimi'`; `compat.js:282-298` then starts that provider. `runtime-dispatch.js:31-46` detects a wire/thread harness mismatch only while creating optional turn authority and continues without it. If a transient lookup error occurred at warmup, the stored OpenCode thread could receive a different wire and fail without an OpenCode session. There is no evidence that this happened at 06:51–06:52; it is a concrete brittleness path worth checking only if future diagnostics show the wire harness differs from the thread harness.
4. **Resource and database pressure are observed, not proven causal.** At approximately 07:35–07:42 UTC, server PID 62366 had 16,133 `lsof` FD records: 16,115 regular files, about 16,091 paths in this checkout and 16,087 distinct checkout paths. About 11,235 were under `ai/RC-MacAir-15/Captures`. The kernel's `kern.maxfilesperproc` is 61,440; the actual process soft limit and FD count at failure time were not measured. The centralized chokidar watcher can subscribe to the project root (`watch/core.js:41-68`, `watch/workspace-watcher.js:150-164`), but the `lsof` snapshot does not establish which owner opened each FD or whether `EMFILE` occurred. The SQLite file was 167,026,688 bytes (40,778 × 4,096-byte pages; 576 freelist pages), with 100,224 `event_log` rows, 99,330 `file:changed` rows, 99,330 resource edges, and 199,553 tags. `dbstat` attributed about 66.9 MB to the event-log table alone; associated edge/tag tables and indexes account for more. Only 185 `file:changed` events were on 2026-09-28 UTC, versus much larger historical days. This is a sizeable ledger, not evidence of a current file-change storm or a SQLite write failure. The receipt and activity writes succeeded before all four failures. The eight prompt receipts occupied one 4 KB table page and one 4 KB index page, so they are not the present bloat source. The receipt schema retains the prompt snapshot until session deletion (`db/migrations/045_prompt_submission_receipts.js:3-20`), a longer-term retention consideration rather than this incident's cause.

## Send and recovery behavior

- The client sends an exact `threadId` and minted `requestId` only on an open WebSocket and records a pending or uncertain attempt after enqueue (`fusion-studio-client/src/state/slices/chatSlice.ts:344-386`, `fusion-studio-client/src/components/chat/useChatSessionActions.ts:103-147`). Server routing checks the live workspace binding, serializes the same request key, and runs admission (`fusion-studio-server/lib/ws/client-message-router.js:720-758`, `fusion-studio-server/lib/thread/prompt-submission-service.js:19-32`). The accepted receipt and visible-group activity share one transaction (`prompt-submission-service.js:103-120`). The user bubble is committed only from `message:sent` (`fusion-studio-client/src/lib/ws/thread-handlers.ts:325-368`). This matches the current Chat Wiki server-owned acceptance contract.
- Before acceptance, missing thread, stale workspace, warmup failure, missing canonical send, or activity failure rejects or cancels the reserved receipt (`runtime-prompt-admission.js:82-185`). After acceptance, metadata or session ownership failure marks `failed_before_dispatch` (`runtime-prompt-admission.js:187-239`); a failed durable dispatch claim does likewise (`runtime-dispatch.js:129-143`). Those branches do **not** match I-007's `execution=claimed`. A session that was merely late to bind before acceptance therefore does not explain these four receipts.
- Claimed dispatch failure stores only `reason=provider_failed` (`runtime-dispatch.js:171-182`). Public status maps every claimed receipt to `unknown_after_dispatch_claim`, even when that reason exists (`prompt-submission-service.js:49-61`), because it cannot prove whether execution reached the provider. The direct `accepted_execution_failed` frame can show the observed “could not start” warning if the renderer has not observed a matching assistant turn (`runtime-dispatch.js:220-245`, `fusion-studio-client/src/lib/chat/prompt-submission-recovery.ts:382-399`). The warning is therefore a safe user-facing state, not proof that no child process ever started.
- The client blocks a new send for `pending`/`unknown` acceptance, but not for an `accepted` attempt waiting for `turn_begin` (`useChatSessionActions.ts:90-105`). The server's `IN_FLIGHT` runtime reservation prevents simultaneous dispatch to that same session (`runtime-activation.js:64-74,125-130`); an impatient second send can still be enqueued and then rejected as busy. This is a user-visible brittleness path, not evidence for the four claimed failures.
- The diagnostic report is persisted only for a genuine `HarnessRuntimeError` candidate after a bound turn ID exists (`runtime-dispatch.js:183-200`). Raw spawn errors, missing-session-ID errors, and other plain exceptions become generic terminal failures without a diagnostic candidate (`harness/opencode/index.js:171-175,287-312`, `thread/turn-terminal-error.js:84-100`). The live `harness_error_diagnostics` count was zero. The server log tee appends `console.log` only and collapses request diagnostics; it does not append `console.warn/error` (`fusion-studio-server/lib/logging.js:29-55`). At 06:51–06:52 the live log contained 97 lines, 82 `request_log` and 15 `diagnostic_log`, no exact exception. Existing logs cannot settle the cause.
