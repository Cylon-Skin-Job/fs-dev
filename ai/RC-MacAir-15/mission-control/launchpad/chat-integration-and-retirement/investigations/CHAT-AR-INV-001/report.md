## Decision answer

Do not freeze the present accepted-message failure/recovery UX into the first plugin/view consumer contract. The prompt receipt is durable, but a claimed provider failure remains indefinitely projected as execution-unknown, and a fresh renderer with no saved exchange cannot reconstruct that accepted user message for the requested conversation review. These are concrete behavior gaps, not evidence that the provider received or rejected a particular prompt. The current Side Chat header also contradicts recorded owner direction. A narrow repair should preserve server-owned acceptance, exact `threadId` routing, and the no-automatic-redispatch rule.

## Findings

### F1 — High: a known local failure remains an unresolved claimed receipt, while foreground UI drops the status control

**Evidence.** `runtime-dispatch.js:129-155` durably claims dispatch before invoking `_sendMessage`; its catch path records `reason='provider_failed'` (`:171-183`) and emits `accepted_execution_failed` (`:220-245`). `prompt-submission-repository.js:46-49` writes that reason but leaves `execution='claimed'`. `prompt-submission-service.js:49-60` projects every claimed receipt as `unknown_after_dispatch_claim`, even with the failure reason. The integration test explicitly codifies this result (`test/ws/prompt-submission-recovery.integration.test.js:93-107`). The client handles that status as uncertain (`prompt-submission-recovery.ts:326-345`), but a foreground `accepted_execution_failed` calls `noteAcceptedExecutionFailure`, which settles and deletes the execution watch (`:382-394`). The connected composer only exposes **Check status** for an accepted attempt with that watch (`ConnectedChatComposer.tsx:79-84`). REF-007 records four live accepted/claimed/`provider_failed` receipts and no new exchange for the user's reported failure window.

**Assessment.** Source-confirmed recovery gap, not a proven standards violation: preserving `unknown_after_dispatch_claim` is a sound way to avoid asserting that an externally claimed provider action never happened. The foreground warning says response could not start, yet receipt readback cannot classify a terminal outcome, and the button to inspect status disappears. The user can send a new prompt after the warning (`chatSubmissionStore.ts:37-40`; `ChatAreaFooter.tsx:98-103,147-151`). That increases ambiguity for the next consumer and makes the warning's instruction to review the conversation harder to act on. The exact cause of the four runtime failures remains unknown; an isolated later CLI success in REF-007 does not settle it.

**Authority and minimum remedy.** The Chat protocol says same-key status must never redispatch provider work (`Wiki/007-Chat_System/002-Harness_And_Event_Flow/004-WebSocket_Protocol/PAGE.md:167-172`); the State standard assigns backend ownership of durable runtime readiness and errors (`Wiki/005-Enforcement/001-Code_Standards/003-State_Management/PAGE.md:21-29`). Preserve those rules. Give the client a durable, content-safe way to distinguish *known terminal local failure* from *external execution genuinely uncertain*, or keep the status affordance until readback is meaningful. Do not turn `provider_failed` alone into proof that no external dispatch occurred. A focused test should cover claimed failure before provider output, foreground error, reconnect/readback, and the next deliberate send.

### F2 — High: a fresh renderer can lose the accepted user bubble when the response never creates an exchange

**Evidence.** Prompt acceptance commits the receipt and group activity before `message:sent` (`runtime-prompt-admission.js:169-210`; `prompt-submission-service.js:103-119`). The client creates the user bubble only while it has a matching in-memory `ChatSubmissionAttempt` (`thread-handlers.ts:325-369`; `chatSubmissionStore.ts:34-61`). Passive `thread:opened` returns mirror history, SQLite exchanges, and live turn, but no receipts (`thread-open-handler.js:117-152`). The hydration path preserves existing in-memory accepted bubbles and the latest in-memory accepted attempt across a reconnect (`thread-history.ts:80-131`); those caches are absent after a fresh renderer process. `ThreadRuntimeManager.claimActiveDrain` creates no live turn (`thread-runtime-manager.js:249-270`), and the dispatch error path synthesizes a turn only if one was bound (`runtime-dispatch.js:183-217`). In the REF-007 window, receipts were accepted but there were no corresponding exchanges or OpenCode messages.

**Assessment.** Source-backed failure path; exact fresh-renderer display was not exercised. If a pre-begin failure leaves no exchange/live turn, a reload can show neither the accepted prompt nor its response even though the server still holds the accepted receipt. The existing restart test at `e2e/chat-architecture/future-submit-electron.mjs:350-369` requires one persisted exchange before verifying the durable user bubble (`:225-241`); it does not cover this failure state. This gap matters directly to the user's "Review the conversation" recovery instruction. It conflicts with the owner's preference to avoid deferring an issue when new consumers would compound it (`User Profile/PAGE.md:27-31`) and with the Chat Wiki's stated server-owned acceptance/user-bubble model (`Wiki/007-Chat_System/006-Runtime_Model/PAGE.md:387-415`). The Wiki calls SQLite authoritative for **completed exchanges** (`Wiki/007-Chat_System/001-Identity_And_Persistence/PAGE.md:85-96`), so this is a missing accepted-prompt hydration contract rather than an assertion that incomplete turns must be exchange rows.

**Minimum remedy/check.** Add a bounded public-route test: accept a prompt, fail before `turn_begin`/exchange, terminate renderer, reopen exact `threadId`, and compare visible conversation with the receipt. Design recovery through the existing session/receipt owner, with no duplicate bubble and no automatic resend. If intentional loss of pre-begin prompt visibility is a product choice, record that choice before a plugin consumer relies on it.

### F3 — Medium: Side Chat still exposes a left control the owner explicitly removed

**Evidence.** The Chat UI Wiki records that a Side Chat must not have the left-hand Show threads button or sliding thread-panel behavior (`Wiki/007-Chat_System/004-Chat_UI/PAGE.md:90-94`; `002-Thread_Header/PAGE.md:26-30`). `useChatSessionHost.ts:137` forces collapsed threads for `host==='side-tab'`; `ChatAreaHeader.tsx:109-119` renders the left Show threads button; `useChatSessionActions.ts:231-237` makes it toggle the owning view's outer sidebar. This is already I-006, so it is not a newly discovered issue.

**Assessment and remedy.** Direct owner-intent mismatch and a consumer prerequisite. The Frontend UI standard requires explicit chat identity/action scope and keeps `threadId` session actions distinct from view placement (`Wiki/005-Enforcement/001-Code_Standards/002-Frontend_UI/PAGE.md:54-64`). Remove that Side Chat control in the owning presentation path with an affected UI check before a reusable plugin view copies the header behavior. Preserve the right-hand button's separately unresolved future behavior.

### F4 — Conditional retirement risk: live compatibility paths can still override canonical history when exchanges are empty

**Evidence.** `thread-crud.js:40-52` passes an optional group resolver; `thread-open-handler.js:23-39` falls back to a bare `threadId` projection when it is absent. `thread-open-handler.js:117-152` still sends both mirror `history` and SQLite `exchanges`, and `thread-history.ts:97-103` uses mirror history whenever exchanges are empty. This overlaps I-005. The Code Standards router's accepted-replacement rule calls for deleting obsolete production shims (`Wiki/005-Enforcement/001-Code_Standards/000-Code_Standards/PAGE.md:75-82`), and the persistence rule treats SQLite exchanges as canonical while mirrors are projections (`Wiki/005-Enforcement/001-Code_Standards/007-Persistence_And_Metadata/PAGE.md:154-164`; Chat identity Wiki `:85-111`).

**Assessment and next check.** Reachability of a missing resolver in the supported production graph and the stale-mirror/empty-exchange state was not proven. Do not call this an active security defect or delete it on this review alone. Exercise those two cases through the public open route; then retire unreachable compatibility or explicitly document a supported fallback and its authority. A plugin consumer should not be promised the fallback as a stable contract until that decision is made.
