### Chat modularity against current standards — 2026-09-28 22:05 UTC

The owner asked whether the current chat implementation is simple and focused enough under the Code Standards and their Ousterhout-inspired design philosophy. Bounded current-byte review finds substantial positive decomposition: server authority owns accepted prompts and exact thread runtime, adapters contain native OpenCode translation, and many connected/presentation surfaces are focused. This is partial alignment, not a complete certification. The standards ask for one job per file, treat over 400 lines as a strong split signal, and prefer deep modules that hide complexity rather than more layers for their own sake.

The clearest excess is in transport entry points. Server `client-message-router.js` (918 lines) multiplexes unrelated domains but also validates/adopts prompts, coordinates view readiness and handles connection teardown inline. Client `ws-client.ts` (665 lines) owns authentication/reconnection and a broad set of domain response/store branches. Client `stream-handlers.ts` (509 lines) protects the live sequence frontier while also applying post-terminal metadata/autocomplete and accepted-prompt errors. Several connected chat hosts/actions send on `state.ws` directly, while the central `sendFusionMessage` has an authenticated, generation-aware boolean result; prompt recovery types that callback as `void`, losing a false-send signal. This is source-backed brittleness but not proof of the observed incidents' cause. The 407-line `ChatComposerModelMenu` is mostly a single menu job, yet it obtains an OpenCode-specific catalog inside presentation; consider its connected/presentation seam, not an automatic split. I-005 separately tracks reachable legacy history/open paths.

The recommended simplification order follows the failure boundary: verify/repair prompt-status and pre-begin accepted-message recovery, consolidate chat intent sends through an existing acknowledged transport owner, reduce inline server/client router policy into existing domain handlers, then retire confirmed legacy paths. Preserve one central ingress and the live frontier invariant; a broad file-splitting pass or new framework would add risk without a clearer contract.
