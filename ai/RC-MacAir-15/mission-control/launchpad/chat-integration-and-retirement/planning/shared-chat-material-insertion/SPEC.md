## 4. Observable destination and insertion contract

### 4.1 Begin, prepare, commit

The existing action boundary exposes a compose-only material operation with a begin snapshot and one commit result. Concrete types/names can be chosen by the builder within these requirements; the API cannot accept send/create options. Continue using the existing app-lifetime `fusion:chat-action` consumer/result ownership, or a directly equivalent extension of that owner, not per-mounted listeners.

1. **Begin synchronously at material action start.** Global caller resolves the current active open mounted chat; composer caller supplies its explicit committed owner. Capture immutable `workspaceId`, `viewId`, `threadGroupId`, `threadId`, `surfaceId`, host/binding kind, mount lifetime generation and, for Side, exact placement identity. Capture workspace activation/hydration generation as needed to prevent leaving/returning from reviving a cancelled operation. Do not invent durable/session IDs.
2. **Validate before source preparation.** No valid owner means a bounded unavailable result and no source work, draft/attachment mutation, Send, new chat or fallback. Missing/unhydrated/foreign tuples do not become valid from `currentThreadId` or an attachment path.
3. **Source prepares independently.** Supply its captured request inputs/socket/resource root/workspace; it returns text or one existing `ChatLinkAttachment`. Capture/save, clipboard lookup, recents selection, transcription and diagnostic validation stay source-owned. No source writes pending attachments/drafts or resolves a replacement destination after await.
4. **Revalidate immediately before mutation.** The shared owner checks the captured tuple/token, current hydrated authority, session existence, exact Side placement if applicable, source cancellation and applicable existing acceptance gate. It never re-resolves global focus. The check and local store mutation execute in one synchronous commit path; no intervening await creates another identity race.
5. **Insert through existing stores once.** Text writes only the captured session's draft through `setDraft`; attachments use `addPendingAttachment`, preserving deterministic IDs, order, deduplication and generation semantics. The result distinguishes applied/no-op duplicate, cancelled, unavailable/busy, invalid material and source failure so callers do not claim a failed insertion succeeded. No retry into a different chat.
6. **Presentation follows the result.** Source-specific success/failure statuses remain concise. Focus/caret restoration occurs only through the originating live presentation adapter and never steals focus from a newly active different chat/view. Store subscribers render exact-owner text/pills; controller touches no DOM.

Preserve composer cursor insertion/replacement for clipboard/recents/microphone text and paragraph append for global/diagnostic text. Pass current exact-owner selection data from a live presentation adapter into commit; calculate against the latest owner draft. Accept cursor offsets only from that same live binding/generation when its editor value/revision matches the latest draft and offsets are in range. Do not overwrite intervening typed text using a pre-preparation draft or read a rebound input ref. Selection is transient editor data, not destination authority; unsupported/stale selection must use a safe paragraph append of prepared text to latest draft rather than overwrite it. Tests cover typing during a delay and cursor behavior without focus theft. This is bounded preservation of existing behavior, not a new insertion mode UI.

### 4.2 Active open global chat

At action start, read one transient active-mounted-chat projection owned by the existing Chat state slice/store. Connected hosts register/remove exact committed mount bindings; explicit row/session/tab activation and actual pointer/keyboard interaction with a chat publish that owner as active. Source/global button focus must retain the last actually active chat. Main re-render, unrelated response arrival, registration order or a stale Side placement cannot steal activation. Initialize only from an unambiguous actually activated valid host; ambiguity/missing activation produces `no_target`, not Main preference.

The record must identify a valid open chat in the active workspace and foreground owning view at **begin**. Main and Side are equally eligible; Main focus after Side focus selects Main even if the content tab remains Side-selected, and Side activation selects Side despite a selected Main row. Closing/collapsing/unmounting a destination composer removes its eligibility; no valid active record yields unavailable. The helper must not substitute `currentThreadId`, selected Main population or Legacy when the active record is missing/stale. An actual foreground Main open/selection may publish its own valid mount, which is direct activation rather than a fallback. Hidden views never register themselves as the global active destination simply by mounting.

After begin, another chat/view may become active. The captured operation remains valid if its exact composer stays bound/open and hydrated. A hidden-but-retained composer is still that owner. If navigation actually unmounts/rebinds it, cancellation is caused by that lifetime change, not by `currentPanel` comparison. Do not restore an old operation when a tuple is reopened with a fresh generation.

### 4.3 Composer identity and validity

Every Add-menu control uses its composer binding regardless of another active chat/view. View-bound Main must cancel if selection changes its actual composer tuple; explicit Main content components keep their own session independently of the outer rail. A Side composer validates its exact open service-managed placement, including adapterless views; requiring a Main row would incorrectly deny a valid Side placement.

A committed lifetime token invalidates on actual owner tuple change, unmount/closed composer, loss of session/workspace/hydration authority or Side placement close/replacement. It must stay invalid after return/remount/reopen, even with equal strings. Changes only to `isActive`, `currentPanel`, unrelated Main group selection or other focus do not invalidate a retained same binding. `surfaceId` alone is not permission: combine it with its live generation and hydrated tuple/placement authority. Duplicate mounts share session draft/attachments but have independent lifetime, cursor/menu and activation state; one operation has one initiating mount and one insertion.

Keep existing `pending` prompt acceptance blocking insertion that would alter the accepted composer; `unknown` permits editing/attachment insertion but not a second Send. Read the established submission store, do not duplicate admission rules or clear/rekey pending attempts.

Preserve existing warm-on-intent behavior on paths that already warm: `useChatSessionActions` attachment/text insertion and `chatScreenshotCapture` successful attachment use the existing panel-store `warmThread` owner. Use the captured exact thread, with the existing warm eligibility/admission policy; no newly resolved active thread or second warming consumer. Existing `isActive`/`chatActive` and pending/unknown guards may suppress warming without cancelling otherwise valid insertion. Input-focus, paste and explicit Send warm fallback remain existing owners. Global resource/diagnostic paths that currently do not warm gain no new warm mandate. Warming is separate from compose-only insertion success: it creates no prompt, user bubble or new chat, is not server acceptance/persistence, and its suppression/failure must not redirect or undo valid local material. Retain the Chat UI Input And Warm Intent contract while replacing only the destination/insertion bypasses authorized here.

### 4.4 Screenshot correlation and failures

Screenshot source captures/saves only after shared begin succeeds. Snapshot the source socket/workspace before native capture; use the existing `screenshot:file-capture` request ID and `screenshot:file-captured`/`screenshot:error` response. Only its correlated saved-path response produces the attachment. Preserve original saved absolute path and `Data/Screenshots/<basename>` relative metadata; never rebuild a destination using later panel state. Retain 30-second deadline and cleanup of timer/message/close resources on every terminal path; duplicates/foreign responses cannot commit twice.

Check shared cancellation after native capture before requesting save, and at final commit after save. Cancellation before save causes no save request; after a save has begun its PNG may remain in the source workspace gallery, with no chat attachment and no deletion/rollback claim. Native capability unavailable, empty capture, source/save error, send exception, disconnect/timeout, invalid material, target deletion/closure and acceptance busy leave drafts/attachments unchanged and report an honest result. Save-server workspace/path protection remains authoritative. Global focus changes alone do not cancel an otherwise valid screenshot.

No migration is required: reuse local session-keyed draft/attachment format, existing managed placement descriptors and direct save protocol. Remove superseded screenshot destination/fallback/direct-store insertion helpers once their callers migrate; no feature flag/parallel legacy material path or persisted active-surface record.
