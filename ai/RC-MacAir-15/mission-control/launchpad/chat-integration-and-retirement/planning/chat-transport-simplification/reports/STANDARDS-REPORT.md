## Ordering and deferral implications

Recommendation, not an approved order: establish the exact common send outcome contract before migrating callers, then make the status-query consumer handle that contract. If candidate 1 extracts the connection owner on which candidate 2 depends, its interface should settle first. Standards alone do not prove candidate 3 must wait for both refactors; the code investigator should determine whether a narrow boolean-handling repair can precede migration without rework or duplicated ownership. Keep three candidates and record the actual dependency edges.

D-005 explicitly parks the broader failure map, accepted/no-response UX, retry/liveness visibility and durable failure readback. User Preferences, **Scope and the 80/20 Preference** and **Intake, Shaping, and Delivery**, permit deferred work only when intervening changes do not impair or compound the later correction. Therefore each candidate should preserve request identity, typed uncertain outcomes, current receipt/service ownership and a place for richer future status. A generic boolean contract that erases existing uncertainty would conflict with this rule. So would automatic resend/cancel based solely on failed status transmission. If the actual proposed interface requires either behavior, hold that affected progression and return the tradeoff to the owner.
