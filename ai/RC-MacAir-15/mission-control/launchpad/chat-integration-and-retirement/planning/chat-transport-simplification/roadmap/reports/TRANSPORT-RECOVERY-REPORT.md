## R1 — recommended executable contract

This is an implementation recommendation under the settled intent, not existing behavior or owner approval.

Use a discriminated local result equivalent to:

```ts
type ProductSendResult =
  | { status: 'enqueued'; destination: 'socket' | 'auth_queue' }
  | { status: 'uncertain'; reason: 'send_failed_after_enqueue' | 'send_outcome_unknown' }
  | { status: 'not_enqueued'; reason: /* bounded local reason vocabulary */ string };
```

The final reason vocabulary should be closed in the authored contract. It must cover disconnected/retired, stale connection, unavailable or stale workspace binding, auth not ready for socket-only callers, serialization failure, queue refusal and proven pre-enqueue send failure; prompt's no_target/invalid_request remain its domain validation outcomes. Never place raw exception text or content into diagnostics through this result.

1. **Single physical product-send owner.** The extracted transport owner resolves the live authenticator/socket, serializes once, validates the caller's expected connection/workspace context, and returns the rich result. Keep the auth-proof send internal and separate from product intent. Avoid importing the full ws-client router into chatSlice and creating a new store/router dependency cycle; the extracted outbound owner can receive lifecycle state through a narrow installed connection dependency.
2. **Explicit queue policy.** Prompt and migrated raw-socket callers retain socket-only behavior unless their existing owner explicitly queued. Existing generic queue-eligible callers, including receipt recovery, retain bounded queue admission. Queue eligibility is a local option, not a new wire field or retry policy. `enqueued/auth_queue` means only this connection's local queue accepted custody, never socket delivery, server acceptance, provider dispatch, or an eventual successful flush.
3. **Exact local binding.** Workspace-bound chat calls carry an expected workspace ID captured from their explicit owner, plus the current transport binding token/epoch/revision and connection generation/socket identity as appropriate. Validate against the live tuple at enqueue and immediately before any queued flush. Use the already applied transport binding, not `hasReceivedInit` alone. Before a tuple exists, refuse workspace-bound work rather than substituting a visible old workspace. `beginInit` invalidates the old tuple; a same-ID new epoch must not rescue stale work. These are local stale-work checks; do not add client authority fields to canonical wire payloads or duplicate server membership validation.
4. **Queue lifecycle.** Preserve FIFO, bounds and auth-lane order. A queued item retains its captured context and lightweight current-context predicate; do not retarget its payload during flush. A stale item is discarded. Auth failure, queue overflow, connection retirement and generation replacement clear retained frames; no replacement connection inherits them. On a flush exception, retain current fail/close behavior and discard remaining frames. Already returned auth_queue admission is not retroactively server failure or original-prompt rejection.
5. **Exceptions.** Move the current prompt enqueue classification into the lowest actual socket-send owner rather than mapping auth's caught false. Preserve the existing increased-buffer→uncertain distinction and definite local pre-enqueue outcomes. For a catch whose position/buffer observation cannot prove the current source's pre-enqueue condition, return uncertain, not false/not_enqueued. Catch serialization before attempting the socket: that invocation is not_enqueued. A close/retirement triggered by send may run synchronously in fixtures; callers must revalidate their generation/entry after the send returns before arming work.
6. **No queue completion callback is necessary for C3.** C3 may start its bounded response deadline at local queue admission, explicitly meaning an inquiry wait budget rather than proof bytes left. If flush later drops/refuses the query, the existing timeout/unknown or connection/workspace retirement path covers it. If workspace changes, that attempt is suspended and later status recovery addresses the same original identity on a qualified binding. Do not add receipt-like transport persistence, auto replay, or callback machinery merely to know the instant of flush. The R2 inventory must verify each other queue-eligible caller already owns bounded timeout/retirement cleanup; it may not silently introduce indefinite pending state.
7. **Caller consumption.** Prompt keeps its rich domain result and existing draft/unknown gate. Domain callbacks may preserve a local boolean API where it only means whether an operation was locally attempted, but they must explicitly handle uncertain and must not infer server success. Existing non-chat boolean APIs can remain a thin translation of the same physical owner where scope requires compatibility; no migrated chat caller may bypass the rich boundary or classify a caught false as definite prompt non-delivery.

Retaining the queue destination as a result field is sufficient; a fourth global chat phase or new message family is unnecessary. The public route's request IDs, immutable prompt snapshot, server receipt owner and action acknowledgements are unchanged.

## R3 — current recovery and minimal transition change

`src/lib/chat/prompt-submission-recovery.ts` owns both acceptance and accepted-execution watches. Entry identity is workspace+thread+request; execution additionally validates accepted turn ID in status responses. The existing deadlines are 15s acceptance/accepted-execution start, 5s inquiry response, and status-only retry delays 1/2/4/8/15s (`:6–8`). No timer here resends a prompt.

Current `sendAction` returns void (`:41,261`). `queryStatus` (`:123–160`) sets checking/in-flight, increments tries, calls it, and arms the 5s wait even when the underlying function returned false. Catch and timeout already use the desired unknown feedback and bounded status retry. `handlePromptStatusFrame` (`:288–378`) requires `entry.inFlightGeneration === generation`; timeout sets that field undefined. Consequently, a late valid response between timeout and retry, or after final retry exhaustion, is currently ignored. That is the concrete small correlation seam implicated by the draft's late-response requirement.

Recommended states retain the existing controller and presentation:

| Inquiry result / event | Acceptance entry | Accepted-execution entry | Timers / response eligibility |
| --- | --- | --- | --- |
| not_enqueued | Set original attempt unknown if pending; retain draft and send gate; use existing “Delivery status unknown…sending again is paused” feedback | Keep accepted phase and accepted bubble; use existing executionUnknown feedback/event | Clear this inquiry's in-flight lock; arm no 5s response timer; schedule existing bounded status retry only while current/qualified. This inquiry grants no new response eligibility. |
| uncertain | Keep original uncertainty; no local rejection or resend | Keep accepted; no local terminal failure | Retain current inquiry generation as response-eligible, keep the existing checking wait, arm 5s budget if the entry/connection remains current. |
| enqueued/socket or enqueued/auth_queue | Keep pending/unknown phase and existing checking feedback | Keep accepted and existing checking response feedback | Same 5s budget and response eligibility; auth_queue is not proof of wire delivery. |
| 5s timeout | Existing unknown feedback | Existing executionUnknown | Release in-flight lock and schedule existing status retry; preserve eligibility of a possibly transmitted same-attempt response. |
| Matching current receipt arrives, including during retry delay | Apply existing accepted/rejected/cancelled/reserved mapping | Apply existing accepted+turnId and execution mapping | Cancel active response deadline and scheduled retry before processing; terminal settlement deletes the entry; only existing nonterminal mappings schedule another status retry. |
| Workspace tuple invalidation/replacement, socket retirement, new attempt, session removal, live turn begins/settles | Existing suspension/settlement behavior | Existing suspension/settlement behavior | Clear both waiting and response-eligible generation plus owned timers; stale replies cannot settle a new attempt/binding. |

Implement the minimum distinction with one additional per-entry generation marker (name is author choice), such as `responseEligibleGeneration`. `inFlightGeneration` remains the “one inquiry is waiting” lock. A current enqueued/uncertain inquiry grants response eligibility. Timeout/manual recheck changes only the waiting lock. Definite refusal leaves prior same-generation eligibility intact if an earlier inquiry may still answer; it must not erase that evidence. Connection/workspace retirement, replacement attempt and settlement clear both. No per-query wire ID is needed: every repeated status query asks about the same original request and server receipt, so any valid reply for that exact current attempt may reconcile it. Do not accept an unsolicited reply when no inquiry for that generation could have left.

The send call can synchronously trigger connection retirement, store callbacks or a fixture reply. Capture the generation and entry identity before sending; after returning, require the same entry/request/generation and live wait before arming a response timer. Prepare response eligibility before the call if synchronous delivery is supported, then withdraw only newly provisional eligibility on definite refusal, preserving any prior possible inquiry. A response that already settled the attempt must not be followed by an orphan timeout. This is timer/correlation correctness within C3, not a new recovery state machine.

Keep both kinds on the same outcome handler. Acceptance uses store.unknown and retains the pending/unknown Send gate. Execution uses existing feedback plus `fusion:prompt-execution-unknown`; it does not demote accepted or fabricate an assistant reply. Preserve the existing execution result policies: not_dispatched can retry; unknown_after_dispatch_claim remains unknown without automatic provider resend; failed_before_dispatch/interrupted_before_dispatch use existing terminal feedback; live turn begin ends the execution watch. The broader correctness/UX of those policies remains D-005.

Reconnect currently increments recovery generation, clears owned timers, and queries only attempts belonging to the current workspace (`:241–284`). Preserve that trigger from authenticated applied workspace:init and applied workspace switch. Never send status for the old workspace through the new binding. Test same-ID rebind invalidation as well as changed workspace ID; current recovery's subscription observes only activeWorkspaceId, so the authored local transport binding integration must carry the invalidation of a changed epoch/revision without inventing a backend authority field.

Server receipt semantics remain unchanged: `fusion-studio-server/lib/thread/prompt-submission-service.js:19–32,134–152` serializes status with same-key admission; missing status can install a cancellation fence, accepted status never repeats provider dispatch. A failed local inquiry says nothing about whether the original prompt is accepted. Only the authoritative matching rejected/cancelled receipt can permit a new deliberate attempt through existing behavior.
