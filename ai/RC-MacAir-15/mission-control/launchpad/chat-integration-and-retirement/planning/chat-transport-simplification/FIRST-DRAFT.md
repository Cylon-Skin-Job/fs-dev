## Capability skeleton and proposed order

| Candidate | Outcome | Why it is a distinct increment |
|---|---|---|
| C1 — Simplify the two transport entry files | Server `client-message-router.js` delegates domain work to cohesive owners; client `ws-client.ts` separates connection lifecycle from domain response application. Existing public behavior remains observable through those owners. | Structural enabler: lowers the number of unrelated responsibilities that must be understood to change transport. It prepares the shared client boundary used by C2 and C3. |
| C2 — Unify chat command sends | Existing chat callers use one acknowledged client transport owner and receive an outcome that accurately describes local enqueue state. Server acknowledgements continue to determine accepted work. | Removes repeated socket-write decisions across chat commands while preserving each command's identity, ordering and lifecycle contract. |
| C3 — Handle the status-check send result | A receipt-status check that definitely did not enqueue does not spend five seconds pretending to await its response. An ambiguous send remains uncertain. The original prompt is never inferred unsent from a failed status inquiry. | Repairs the concrete ignored-result seam using the outcome contract established in C2. |

Recommended sequence: **C1 → C2 → C3**. C1 makes transport ownership explicit; C2 establishes one honest result contract; C3 consumes it. This minimizes rework rather than expressing a hard semantic dependency: a narrow C3 repair is technically possible earlier, but would then need to adopt C2's result contract. Final slice boundaries and checks belong to Creator. The three candidates share client transport surfaces, so they are not proposed as parallel implementation jobs. Independent preparatory reading may proceed in parallel; shared writes require assigned ownership.

There is already one main user-text route: `useChatSessionActions` → `chatSlice.sendMessage` → `prompt`. C2 unifies transport handling across that route and other chat intents; it does not invent a second prompt workflow. Here, an “acknowledged client boundary” means an explicit local transport result, never a server acknowledgement. Existing canonical families remain `prompt`, `turn:stop`, `thread:*` and `chat-turn:*` according to their established owners. No new general message bus or provider-specific client protocol is justified.

## Candidate slice cards

These stable IDs identify discussion candidates, not approved SPEC or execution slice IDs. Every smoke below is proposed evidence to obtain later; none was run for this draft.

### C1-A — Cohesive server ingress ownership

- **Outcome / intent:** D-004's server-router simplification yields one clear ingress dispatcher and focused domain ownership. This is a structural enabler, consumed by C1-B/C2 and future failure-map work; its value is simpler change boundaries rather than a new user feature.
- **End-to-end path:** authenticated WebSocket ingress → existing workspace/thread/domain owner → authoritative response, persistence or live publication → current client consumer. Extract inline policy into the appropriate existing owner where possible; a new private module needs a cohesive reason.
- **Prerequisite:** current router/handler behavior and per-connection dependencies are understood well enough to preserve initialization, workspace-operation leases, denial order and teardown. Creator supplies the bounded route/ownership inventory before this increment is executable.
- **Smoke scenario:** a connected user opens an existing thread, sends one deliberate prompt, and receives server acceptance and its routed response. A passive open produces history without starting a provider. A denied or superseded workspace request has no provider or persistence effect. Connection closure retires its owned resources once. Select representative non-chat route checks for every responsibility actually moved.
- **Nearby constraints:** retain exact request/thread/workspace identity, accepted-prompt receipt authority, route diagnostics/redaction and post-commit delivery isolation. Do not transfer policy into a second router or split only to meet a line count. Preserve existing trace stages and the temporary logger's removal/migration annotation.
- **Question / excluded scope:** Creator must choose the cohesive extraction seams and regression cases. Existing open/history compatibility retirement, provider failure repair and broad database work are outside this increment.

### C1-B — Cohesive client connection and response ownership

- **Outcome / intent:** D-004's client-router simplification leaves connection/authentication/reconnect concerns distinct from response application through existing domain handlers. This completes C1's structural enabler for C2/C3.
- **End-to-end path:** runtime descriptor and authenticated connection → message ingress/redaction → domain handler → established store owner → visible chat or other affected feature.
- **Prerequisite:** C1-A's contract inventory and current client lifecycle/handler map. The proposed sequencing avoids changing both ends without an observed parity checkpoint; it does not assert a runtime dependency between the extractions.
- **Smoke scenario:** connect and open a thread, receive a streamed reply, navigate away and back, then reconnect. History and the live snapshot remain attached to the exact session; old-generation frames do not change the new connection's state. A live content gap still shows the existing two-second hourglass, then clears according to reveal/terminal behavior. Exercise affected non-chat response families as well.
- **Nearby constraints:** route and frontier validation precede state mutation; preserve `threadId + turnId + streamSeq`, snapshot ordering, post-terminal correlation, authentication ownership and cleanup. Existing portable chat components continue receiving explicit data/actions. Avoid broad `stream-handlers.ts` or live-renderer decomposition as an incidental expansion.
- **Question / excluded scope:** Creator selects the response responsibility seams, moved listener/timer cleanup and stale-import checks. This increment does not redesign the hourglass, infer provider liveness, or change retries.

### C2-A — One client send boundary with truthful local outcomes

- **Outcome / intent:** D-004's unified chat command behavior means a user intent reaches one transport owner with explicit target and connection context, and the caller can distinguish local enqueue success, uncertainty and definite failure where those distinctions are available.
- **End-to-end path:** connected chat action/host → shared authenticated transport boundary → existing canonical server route → existing acknowledgement handler/store → displayed result. Migrate existing chat callers, including the single prompt route, without flattening their domain semantics into one command.
- **Prerequisite:** C1's transport owners are available and public-route parity is established. Creator resolves the bounded enqueue/queue contract against `chatSlice.sendMessage`, `sendFusionMessage` and shell authentication before release: current prompt outcomes include `enqueued`, `uncertain` and `not_enqueued`, while the current boolean sender can queue before authentication and can return false after catching a send exception.
- **Smoke scenario:** from Main Chat and an exact Side Chat, send one prompt and verify the accepted bubble arrives only on `message:sent`. Open/list/Stop and a representative durable thread action use the same transport owner but retain their own targets and acknowledgements. A definite local failure retains the draft; an ambiguous enqueue preserves recovery and does not auto-resend. A reconnect or workspace switch cannot flush a stale command into a different connection/workspace. A migrated durable group action still acknowledges the requester, updates another open window and reads back through its owning state.
- **Nearby constraints:** local enqueue or pre-auth queue admission is not server acceptance, execution start or provider receipt. Preserve one request ID per deliberate attempt, exact workspace/connection generation, domain ownership, canonical payloads and existing server validation. Remove migrated raw-send bypasses within this scope. A safe result contract may extend the current sender; wrapping the current boolean alone does not preserve prompt uncertainty.
- **Question / excluded scope:** Creator determines exact caller coverage and how pre-auth queued work is represented/cancelled on generation or workspace change using current contracts. Internal module and type choices are technical work, not new owner gates. A proposed change to product retry, resend or cancellation policy would require a scoped owner decision and is outside C2.

### C3-A — Receipt-status inquiry handles its transport outcome

- **Outcome / intent:** D-004's concrete false-send repair makes Check status accurately reflect its own request delivery. A definitely not-enqueued inquiry immediately leaves the awaiting-response state through existing recovery feedback; an ambiguous inquiry retains uncertainty instead of claiming definite non-delivery.
- **End-to-end path:** Check status or scheduled receipt query → C2 transport outcome → prompt recovery controller/timer → existing composer status display; when a request reaches the server, the current receipt owner and response correlation remain authoritative.
- **Prerequisite:** C2 exposes a trustworthy outcome to recovery and Creator specifies its mapping to the existing checking/unknown states. The current callback is typed as `void`, discards the boolean result and arms a five-second response wait; current false alone is not proof that no frame could have left.
- **Smoke scenario:** hold one unresolved original prompt attempt, trigger Check status while the transport definitely cannot enqueue, and observe immediate existing unavailable/unknown feedback with no orphan response deadline. Restore the qualified connection and query that same attempt successfully. Separately inject an ambiguous status enqueue, verify uncertainty is retained, and confirm a late matching response still reconciles correctly. Neither path sends the original prompt again, stops OpenCode, creates a second accepted bubble, or releases the pending/unknown send gate by assuming rejection. Preserve both acceptance and accepted-execution recovery entries.
- **Nearby constraints:** status inquiry failure and original prompt failure are different facts. Retain request/thread/workspace correlation, existing bounded recovery scheduling and teardown, and server acceptance as authority. The two-second live-turn hourglass and provider-owned retry loop are not status-query timers.
- **Question / excluded scope:** Creator must specify exact reuse of existing recovery feedback/timer transitions and public-route failure evidence. No new assistant failure row, terminal-state model, retry label, accepted-receipt hydration or provider cancellation behavior is included.
