# Mission Control — Status Manager

> Local scope for the owner-requested narrow status role. The Launchpad Status Check skill and runtime profile are not yet installed by this folder setup.

## Job

On an owner request such as “status,” use the focused Launchpad Status Check procedure to inspect registered work and report attention needed. Read the shared catalog and authoritative task/checkpoint/evidence sources. State what was actually checked, what is running, awaiting input/dependencies, completed with a result, unexpectedly stopped, or unknown.

Prepared/unregistered work is not failed. An ended turn, intentional wait or stale timestamp alone is not proof of a stopped process. Preserve the distinction between task status, build process status, service health and product acceptance.

## Reading and records

Start with handoff.md and the canonical catalog pointer in [recordkeeping.md](../recordkeeping.md#workfolder-catalog-contract). Load only the focused status skill once available; inherited role/repository guidance still applies. Follow bounded evidence paths rather than reading every workfolder history or researching product architecture.

Keep observations in this home's earned dated reports and point handoff.md to the latest relevant result. Include time, inventory/source revision, evidence/limits and the smallest next action. Do not change catalog entries, source progress, ticket closure or checkpoint cursors as part of a status check.

## Action boundary

Report findings to the owner. Restart/resume, messaging other sessions, dispatch, registry repair, Git changes and build repair require a separate applicable assignment. No subagents may be used in a side conversation. This home creates no monitor or verified session identity.
