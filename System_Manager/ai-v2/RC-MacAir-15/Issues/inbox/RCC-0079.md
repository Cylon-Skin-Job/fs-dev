Solobooks does not ship with the Fusion Studio binary. It is downloaded on demand, with a licensing modal, and supports both local-free and cloud-synced modes.

---

## 1. Solobooks Download & Licensing Flow

### Download Trigger
- User selects "Add Solobooks" from Electron menu or AI chat
- Fusion Studio downloads the Solobooks repo from GitHub (or private registry)
- Download happens **after** user accepts the license terms

### Licensing Modal (First Open)

```

│                                                         │

└─────────────────────────────────────────────────────────┘
```

- **Cancel:** Abort download, do not create workspace
- **Agree:** Download repo, create workspace, store acceptance timestamp in `ai/<machine>/System/state.json`

**Trust model:** Users can bypass this by downloading the repo directly or forking. The modal is a good-faith gate, not DRM.

## 3. Cloud Sync Architecture

### Modes

**Local Mode (default):**
- All data in `workspace.db` (local SQLite)
- No network calls
- Free forever

**Cloud Mode (Pro):**
- Web backend at `api.solobooks.ai`
- Mobile apps (iOS/Android) share the same backend
- Desktop syncs via API
- Web interface for browser access

### Sync Trigger

User flips a switch: **"Use Cloud as Source of Truth"**

```
┌─────────────────────────────────────────┐
│  Sync Settings                          │
│                                         │
│  [●] Local Only                         │
│  [○] Cloud Source of Truth              │
│                                         │
│  When cloud is source of truth:         │
│  • Desktop uploads on change            │
│  • Desktop pulls on workspace switch    │
│  • Background poll every 15 minutes     │
│                                         │
└─────────────────────────────────────────┘
```

### Background Polling

- Poll interval: **15 minutes** (configurable)
- Also poll on: **workspace switch** (user selects Solobooks workspace)
- Poll mechanism: Check cloud `last_change_id` against local `last_pull_id`
- If cloud is newer → pull changes
- If local is newer → push changes

```js
// Pseudocode
async function syncIfNeeded() {
  const cloud = await api.getLastChangeId();
  const local = state.get('solobooks.last_pull_id');
  
  if (cloud.id !== local) {
    const changes = await api.pullSince(local);
    applyChanges(changes);
    state.set('solobooks.last_pull_id', cloud.id);
  }
}

// Every 15 minutes
setInterval(syncIfNeeded, 15 * 60 * 1000);
```

### Conflict Resolution

- Last-write-wins per transaction
- If both local and cloud changed since last sync, cloud wins (it's "source of truth")
- User can manually force "local wins" in settings

## 4. Workspace Lifecycle UEB Events

New UEB events for workspace state transitions:

| Event | When | Payload | Use Case |
|-------|------|---------|----------|
| `workspace:selected` | User switches to this workspace | `{ workspaceId, previousId }` | Trigger sync, refresh data, run hooks |
| `workspace:ribbon_added` | Workspace added to ribbon | `{ workspaceId }` | Initialize state, warm caches |
| `workspace:ribbon_removed` | Workspace removed from ribbon | `{ workspaceId }` | Soft-reset state, pause sync |
| `workspace:script_run` | Run automation scripts on event | `{ workspaceId, trigger }` | Custom user scripts per workspace |

### Subscription Pattern

Views and scripts can subscribe to workspace events:

```js
// In a view's app.js
fusion.subscribe('workspace:selected', (event) => {
  if (event.workspaceId === myWorkspaceId) {
    syncIfNeeded();
  }
});
```

### Script Execution

User can attach scripts to workspace lifecycle events:

```
ai/scripts/
├── on-workspace-selected.js
├── on-workspace-added.js
└── on-workspace-removed.js
```

These run in the server process (sandboxed VM), not the renderer.
