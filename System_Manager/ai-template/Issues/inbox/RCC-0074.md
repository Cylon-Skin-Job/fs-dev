Replace traditional setup wizards with **ticket-driven onboarding**. The AI checks a ticket registry on every "New Chat" and offers to continue incomplete checklists. Users stop and resume anytime — progress lives in the ticket, not in a modal.

### Core Idea

No setup wizards. No blocking popups. No confusion about where you left off.

1. **Onboarding is a ticket.** "Fusion Studio Onboarding Checklist" lives in the Issues viewer like any other ticket.
2. **A ticket registry** declares which tickets are "special" (onboarding, update checklists, workspace setup).
3. **On New Chat**, the AI scans the registry. If an onboarding ticket is incomplete, it auto-injects the context:  
   > *"I see you haven't finished First-Time Setup. Want to continue? Here's what's left: [checklist]."*
4. **Progress is the ticket state.** Check off items, move the ticket to `complete/` when done. The AI reads the current state on each chat.

### Ticket Registry Format

A new `registry.json` in `ai/views/issues-viewer/content/`:

```json
{
  "version": "1.0",
  "triggers": [
    {
      "ticket_title": "Fusion Studio Onboarding Checklist",
      "match_field": "title",
      "required_state": "open",
      "required_priority": "interrupt",
      "prompt_template": "Begin Onboarding: ai/views/issues-viewer/open/{{ticket_id}}",
      "inject_on": ["new_chat", "workspace_switch"],
      "auto_archive_on_complete": true
    },
    {
      "ticket_title": "App Update Checklist",
      "match_field": "title",
      "required_state": "open",
      "prompt_template": "Begin App Update: ai/views/issues-viewer/open/{{ticket_id}}",
      "inject_on": ["new_chat"],
      "auto_archive_on_complete": true
    },
    {
      "ticket_title": "New Workspace Setup",
      "match_field": "title",
      "required_state": "open",
      "prompt_template": "Begin Workspace Setup: ai/views/issues-viewer/open/{{ticket_id}}",
      "inject_on": ["workspace_switch"],
      "auto_archive_on_complete": true
    }
  ]
}
```

### Priority Levels

| Priority | Behavior | Examples |
|----------|----------|----------|
| **Interrupt** | Auto-injected on every matching `inject_on` event until resolved | First-time onboarding, critical app update, security alert |
| **High** | Pinned to top of Issues viewer, no auto-inject | Post-update checklist, recommended migration |
| **Medium** | Normal queue position, no auto-inject | Active work, standard tickets |
| **Backlog** | Hidden from default view, no auto-inject | Future ideas, wishlist items |

Only **Interrupt** triggers the auto copy-paste. Everything else waits for the user to open the ticket or ask about it.

### AI Injection Flow

```
User clicks "New Chat"
        ↓
AI reads ticket registry
        ↓
Any matching tickets with state === 'open' AND priority === 'interrupt'?
        ↓
Yes → Inject prompt_template into system context
        ↓
AI greets user with context: "I see onboarding is 1/3 complete..."
```

### Why This Beats Wizards

| Traditional Wizard | Ticket-Driven Onboarding |
|---|---|
| Blocking modal, must finish or cancel | Start/stop anytime, resume in any chat |
| Progress lost if app closes | Progress persists in markdown checkboxes |
| One-size-fits-all flow | AI adapts to what's already done |
| No visibility after completion | Ticket lives in archive for reference |
| Can't ask questions mid-flow | It's just chat — ask anything anytime |

### Open Questions

- Should priority be per-ticket (frontmatter) or per-registry-entry (who wins if they conflict)?
- Should the registry support wildcard matching (e.g., `title: "*Onboarding*"`) or exact titles only?
- Should completed onboarding tickets move to `complete/` or stay in `open/` with `state: closed`?
- How do we handle multiple matching tickets (onboarding + app update both open)?
- Should the AI *always* inject, or only after a user-configurable delay (e.g., "don't remind me for 24h")?
- Should onboarding tickets be created by the app on first run, or ship pre-baked in the bundle?
